# LiLi 라우터 경계 평가 v3

v2(`conversation-smoke-v2`)의 10문항을 그대로 두고, 새 문항 32개를 더했다(총 42문항).
v2는 같은 기본 10문항의 반복 안정성을 확인했다. v3는 표현·조건·대화 맥락이 달라질 때 LiLi가 맞게 동작하는지를 본다.

- 생성: `python Evaluation/datasets/conversation-smoke-v3/build_cases.py` (저장소 루트에서 실행)
- 표시 목록과 이전 대사: 실측 `20261105-lili-v2-gx1`에서 앱이 실제로 받은 결과와 LiLi 대사를 가져왔다.
  - `855f2052-…`: 종로 왕실 거처 추천 결과
  - `2a6210ab-…`: 173을 뺀 뒤의 종로 관광지 결과
- 인용 가능한 원문이 있는 장소는 평가 환경 기준 378(창경궁, 종로)과 311(올림픽공원피크닉장, 송파)뿐이다. 그래서 `citations: REQUIRED`는 이 두 곳이 결과에 나와야 하는 문항에만 둔다.
- 정답(기대 동작)은 Claude가 작성한 초안이다. 실측 전에 사용자 검토를 받는다.

## 새 문항

| 묶음 | 수 | 무엇을 보나 |
|---|---|---|
| A. 다른 표현 | 10 | 같은 의도(검색·대화·되묻기·지원하지 않는 기능)를 다른 말로 했을 때 분기 |
| B. 복수 조건 제외 | 6 | 두 곳·마지막·범위 제외, 범위 밖 순번, 불분명한 지시, 기존 제외 유지 |
| C. 여러 턴 | 8 | 대화 이력을 이어받는 제외·계획·작업 조회, "거기" 같은 지시어, 지역 바꾸기, 말로 준 일정 조건 |
| D. 경계 | 8 | 원문에 없는 운영시간·입장료·주차, 맞는 결과 없음, 카탈로그 밖 지역, 비교, 서버가 거부하거나 실패하는 계획 |

## 새 판정 규칙

| 필드 | 뜻 |
|---|---|
| `lili_branch`가 목록 | 그중 하나면 분기 통과. 예: 일정 조건이 없을 때 LiLi가 직접 되묻거나(`CLARIFY`), 계획을 골랐는데 서버가 되묻는 것(`GENERATE_PLAN`) 모두 맞다 |
| `outcome: ASK_BACK` | 검색·계획 작업을 만들지 않고, 사용자에게 묻는 대답(TEXT)으로 끝나야 한다 |
| `query_terms` | LiLi가 만든 검색어에 이 낱말이 모두 들어 있어야 한다. 대화 이력의 지시어("거기")나 지역 변경을 검색어에 반영했는지 본다 |
| `plan_outcome: REJECTED` | 서버가 계획 요청을 바로 거부한다(예산 지정, 자동차 이동). 작업이 만들어지지 않고, LiLi가 사유를 전한다 |
| `plan_outcome: FAILED` | 작업은 접수되지만 초안 검사에서 실패한다(30분 안에 60분 체류). 작업이 실패 상태로 끝나야 하고, 사유에 내부 용어가 없어야 한다 |
| 기존 제외 유지 | 요청의 `searchContext.excludePlaceIds`가 있으면, 새 제외를 더한 뒤에도 기존 제외가 검색 조건에 남아 있어야 한다 |
| `capability: UNSUPPORTED` | 서버에 없는 기능 요청("예약해 줘" 등)이다. 의도 라벨(PLAN·CONVERSATION)은 판정하지 않고, 기능이 없는 것으로 다뤘는지(대화로 끝나고 도구·작업 없음)를 본다. 할 수 없다고 말하고 되는 기능만 안내했는지는 의미 검수로 본다 |

v2와 다른 점: v2 문항 `CONV-UNSUPPORTED-booking`도 v3 안에서는 같은 `capability` 규칙으로 판정한다(v2는 의도 PLAN을 요구했다). v2 파일 자체는 바꾸지 않았다.

## 실측 후 바꾼 기대 동작

| 문항 | 처음 기대 | 바꾼 기대 | 근거 |
|---|---|---|---|
| `V3-D-hours-and-fee` | 검색 후 "확인되지 않았다"고 말함 | 없는 기능 요청(`capability: UNSUPPORTED`) | 서버에 운영시간·입장료 자료가 없다. 실측 r1·c1 두 번 모두 LiLi가 검색 없이 "확인된 정보 없이 말하면 안 돼"라고 답했고 지어낸 내용이 없었다. 사용자 규칙("기능이 있는지로 판정")에 따라 바꿨다 |
| `V3-D-parking` | 같음 | 같음 | 주차 자료도 없다. 같은 이유 |

질문(입력)은 그대로라 입력 해시는 같다. 바꾸기 전 실측 기록은 바꾸기 전 문항 해시로 남아 있다.

## 알려진 한계

- 여러 턴은 이전 대화를 `history`로 고정해 넣은 것이다. 실제로 앞 턴의 결과를 받아 다음 턴을 이어 가는 연쇄 실행은 아니다.
- `V3-C-conditions-in-text`는 사용자가 말로 준 일정 조건을 서버가 쓸 수 없다는 현재 한계를 드러내는 문항이다. 기대 동작은 앱에서 조건을 입력하도록 안내하는 것이다.
- `V3-D-plan-too-short`는 모델 호출 뒤에야 실패한다. 체류시간만으로 불가능한 요청을 미리 거르는지는 이 문항으로 확인한다.
