# RAG 청크 구조 검토와 후속 계획

외부 설계 제안(장소 → 프로필 → 측면별 Parent → Child 4단 계층, 다축 태그, 예상 질문 별도 벡터, 장소당 15~20개 청크)을 현재 구현과 대조한 기록이다.

- 상태: **보류.** 실제 툴콜링 평가를 먼저 진행하고, 이 문서의 조사·측정은 그 뒤에 시작한다.
- 기준: `develop` `2c419835`.
- 이 검토에서는 코드 변경, DB 조회, 유료 호출을 하지 않았다. 현재 구현에 대한 서술은 저장소 코드를 읽어 확인한 것이다.

## 1. 검토한 제안 요약

- 계층: Place(RDB) → Profile 1개 → 측면별 Parent 6~8개(LLM이 쓴 종합, 800~1,500자) → Child 2~3개씩(200~400자, 검색 대상).
- 태그 축: 출처 유형 / 내용 형태(발췌·요약·사실) / 측면 / 감성 / 대상·계절.
- 예상 질문: 청크당 3~5개(키워드형, 상황형 구어체, 장소명 없는 추천형). 본문과 분리한 별도 벡터로 두고 점수는 최댓값을 쓴다.
- 운영시간·요금·주차 여부 같은 정형 정보는 DB 열로 두고, 청크에는 정성 정보만 담는다.
- 유사도 0.9 이상 청크는 합치고 `mention_count`를 올린다.
- 검색: 의도 분류 → 하이브리드(BM25 + 본문 벡터 + 질문 벡터) → 리랭크 → Parent 확장 → LLM.
- 측정: 근거 일치율, 공식 데이터 대비 사실 정확도, Recall@5, 모름 처리 비율, 카테고리별 체크리스트 답변 가능률.
- 진행: 장소 10~20곳 파일럿 → 측정 → 가장 낮은 단계부터 개선 → 규모 확대.

## 2. 동의하는 판단

- 품질은 검색·리랭커·프롬프트보다 **수집 단계**에서 결정된다. 뒤 단계는 이미 들어 있는 정보를 꺼낼 뿐이다.
- 정형 정보는 DB가 기준이다. 청크와 충돌하면 DB를 따른다.
- "충분한가"는 청크 수가 아니라 **사용자가 물을 질문에 답할 수 있는 비율**로 잰다.
- 지표 없이 규모부터 키우지 않는다. 문제가 수집·청킹·검색 중 어디서 생겼는지 구분할 수 없게 된다.
- 조건 누락("평일엔 여유, 주말 10시 이후 만차"가 "주차 여유"로 줄어드는 것)은 틀린 정보보다 그럴듯해서 더 위험하다.

## 3. 이미 구현된 부분

| 제안 | 현재 구현 |
|---|---|
| 청크에 `evidence`를 따로 두고 원문과 문자열 매칭 | 청크 본문 자체가 보존 원문의 정확한 구간(유니코드 코드포인트 offset)이다. LLM은 본문을 바꾸지 못하고 앞에 붙는 `context_text`만 쓴다. 임베딩 문장은 `context_text` + 원문 구간이다(`embedding-server/app/contextual/contracts.py`의 `SearchChunk`) |
| Perplexity 이중 요약 주의 | Sonar 답변 문장이 아니라 검색·페이지 도구 출력에 실제로 있는 짧은 인용만 받도록 검증한다(`embedding-server/app/enrichment/agent.py`, `evidence.py`) |
| `[장소명 \| 측면]` 접두어, 다른 장소 이야기 섞임 방지 | 문맥이 임베딩 문장 앞에 붙는다. 구간마다 장소 귀속(주체/언급)을 기록하고, 장소 간 관계는 원문 구간을 근거로 둔다 |
| 정형 정보는 DB | TourAPI 필드를 원문 증거로 쓰고(`capture_scope=field`), 적격 장소를 DB에서 먼저 거른 뒤 벡터 검색·리랭킹한다(`metadata_filter.py`) |
| 감정 enum을 이미지와 1:1 | `CharacterEmotion` 10개가 `Resouces/Images/LiLi/catalog.json`과 연결되고 Strict JSON 스키마로 강제된다 |
| `used_chunk_ids`, 장소 ID 검증 | `citations`에 장소 ID·근거 ID·원문 ID·정확한 인용을 담는다. 서버가 응답 항목을 만들고 ID 창작을 막는다 |
| 측면 태그 | 검수 인용에 한해 `ChunkAspect`(주차·후기·장소 설명·체험)가 있다. 관점별 선택 v2는 선택 사항이다 |

## 4. 따르지 않거나 조건부로 둘 것

1. **청크 본문을 LLM 요약으로 두는 스키마**는 따르지 않는다. 제안 스스로 경고한 재작성 위험을 다시 들여온다. 원문 구간을 본문으로 유지한다.
2. **Parent를 LLM이 쓴 측면별 종합으로 만드는 것**은 따르지 않는다. 여러 출처를 합쳐 요약하는 단계가 조건 누락이 생기는 지점이다. Parent가 필요하면 같은 원문 문서의 앞뒤 구간으로 넓힌다(small-to-big). 원문 offset이 이미 있어 싸고 충실하다.
3. **예상 질문 별도 벡터**는 측정 후 결정한다.
   - 현재 청크 생성 검증은 질문 확장을 거부하거나 프롬프트 버전 설정(`allow_hypothetical_questions`)으로 막는다(`embedding-server/app/contextual/agent.py`). 일부러 꺼 둔 상태다.
   - 장소당 벡터가 60~100개 늘어난다. 임베딩·리랭커가 이미 GPU를 쓰고 있어 여유가 적다.
   - 사람이 쓴 holdout 질문으로 Recall@5를 비교한 뒤 켠다. 청크의 예상 질문을 평가 질문으로 다시 쓰지 않는다.
4. **검색 앞단의 의도 분류**는 두지 않는다. 별도 라우팅 모델 없이 단일 LLM이 판단하고 UI 의도 버튼을 힌트로 쓰기로 정했다. 추천과 일정은 이미 `search_places`·`generate_plan` 도구로 나뉜다.
5. **유사도 0.9 이상 병합**은 따르지 않는다. 합치면 출처 구간을 잃는다. 청크는 보존하고, 활성 청크를 고를 때 다양성을 주고 지지 출처 수만 센다.
6. **감성·대상·계절 태그**는 필터로 실제로 쓸 때 추가한다. LLM이 붙이는 태그는 또 하나의 오류원이다. 처음에는 측면과 출처 유형만 쓴다.

## 5. 비어 있는 것

- **답변 가능률 지표.** `cli coverage`는 장소별 활성 청크 **개수**(15개 기준)만 센다. 카테고리별 질문 체크리스트로 "이 청크들로 답할 수 있는가"를 재는 지표가 없다.
- **원문 실태.** 저장된 원문 중 전문(`full_text`)·발췌(`excerpt`)·필드(`field`)의 비율과 길이 분포를 확인하지 않았다. 짧은 발췌뿐인 장소는 복제 없이는 15~20개를 채울 수 없으므로 정보 없음으로 처리해야 한다.
- **측면별 수집 쿼리.** "OO 주차", "OO 아이랑", "OO 단점"처럼 측면을 겨냥한 수집이 없다. 협찬 편향 때문에 단점 쿼리가 특히 필요하다. 이름이 같은 장소가 섞이지 않게 지역·주소를 쿼리에 넣는다.
- **고유명사 검색.** 검색 코드에서 BM25나 이름 유사도(`pg_trgm`) 검색을 찾지 못했다. 이름 질의는 DB 이름 매칭으로 먼저 거르는 편이 BM25를 붙이는 것보다 싸다.
- **교차 확인 등급과 작성일.** 출처 2개 이상(confirmed)과 단일 출처(single_source) 구분, 오래된 청크의 가중치 조정이 없다.
- **모름 처리 문항.** DB에 없는 정보를 물었을 때 지어내지 않는지 보는 평가 문항이 따로 없다.
- **저작권.** 블로그 전문은 화면에 그대로 노출하지 않는다. 짧은 인용과 링크 수준으로 쓴다.

## 6. 툴콜링 평가 이후 순서

1. **원문 실태 조사(DB 읽기 전용, 비용 없음).** 장소별 출처 수, `capture_scope` 비율, 원문 길이 분포, 활성 청크 수.
2. **파일럿 답변 가능률 측정.** 카테고리가 다른 장소 10~20곳.
   - 체크리스트 예: 자연·관광지는 소요시간·난이도·주차·혼잡 시간대·입장료·아이·노약자 동반·계절·편의시설·포토스팟·연계 코스. 카페·식당은 대표 메뉴·가격대·웨이팅·주차·좌석·분위기·아이·반려동물 동반·영업시간·단점.
   - LLM 판정에 사람 표본 검수를 더한다. 여러 장소에서 같은 측면이 비면 수집 쿼리 문제이고, 특정 장소만 낮으면 웹에 정보가 없는 것이다.
3. **수집 보강.** 가장 낮게 나온 측면을 겨냥한 쿼리를 추가한다.
4. **확장 기법 비교.** 질문 확장, small-to-big Parent, 이름 매칭을 사람이 쓴 holdout 질문으로 비교한다(Recall@5, GPU 사용량).
5. **추천·설명 품질 평가.** 2번 측정 뒤에 해야 결과를 해석할 수 있다.

제안이 시작점으로 둔 목표 수치는 다음과 같다. 업계 표준이 아니라 파일럿 기준값이다.

| 지표 | 측정 | 시작 목표 |
|---|---|---|
| 근거 일치율 | 인용이 원문에 실제로 있는지 자동 매칭 | 90% 이상 |
| 사실 정확도 | 운영시간·요금·주차 여부를 공식 데이터와 비교 | 불일치 10% 미만 |
| 검색 정확도 | 사람이 쓴 질문-정답 청크 50~100쌍, Recall@5 | 0.8 이상 |
| 모름 처리 | DB에 없는 정보를 묻는 질문 20개에서 지어내지 않은 비율 | 90% 이상 |
