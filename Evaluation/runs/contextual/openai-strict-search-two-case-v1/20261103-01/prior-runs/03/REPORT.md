# category 수정 반영 확인 및 기존 2문항 재시험 중단

수정된 category 스키마가 실제 평가 서버의 요청 본문에 반영됐음을 확인했다. 서버 분류 검증 코드도 이번 JAR에 포함됐다. 하지만 첫 문항이 기록용 중계기에 추가한 스키마 비교 검사에서 차단돼 `COUNT_UNAVAILABLE`로 중단됐다. 두 번째 문항은 실행하지 않았다. 모델의 실제 category 선택과 기존 빈 검색 결과 문제가 해소됐는지는 확인하지 못했다.

## 반영 확인

- 평가 서버 PID: `35572`, 평가 포트: `18080`. 실행 경로가 새 실행 폴더의 JAR·설정을 가리키고 해당 PID가 포트를 소유함을 확인했다.
- JAR SHA-256: `48b849b79f2381b85fbc1fb131532b720a317d2e85e23f3b4d51f47fe6462c79`.
- `SearchPlacesContract`, `PlaceSearchCriteriaResolver`, `SearchPlacesTool`, `PlaceSearchCategories`, `PlaceSemanticSearchService`와 기존 예산 가드의 패키징된 클래스가 이번 컴파일 결과와 바이트 단위로 일치했다.
- 새 category 계약·strict 계약·기존 예산 가드를 합친 오프라인 검사 51개가 통과했다. 실행 중 invalid category 거부를 별도 요청으로 재검사하지 않았다.
- 실제 서버가 보낸 원본 `received-01.request.json`에는 저장 분류 8개를 열거한 category enum과 null 허용, 세부 특성을 query에 유지하라는 설명이 들어 있다. 이 사실은 스키마 배포 확인이며 **8개 분류의 실제 모델 평가 결과가 아니다.**

증거: `../deployment-verification.json`, `../server-process-verification.json`, `../provider-schema.expected.json`, `received-01.request.json`.

## 중단 원인

내가 이번 실행 중계기에 추가한 검사에서 실제 도구 스키마와 빌드 시 내보낸 스키마를 JSON 배열의 순서까지 포함해 비교했다. 두 스키마의 차이는 최상위 `required` 배열 순서뿐이었다. 필드 집합, category 허용값과 나머지 내용은 같았지만 비교 검사가 요청을 차단했다. 애플리케이션은 로컬 HTTP 400 응답을 받아 `COUNT_UNAVAILABLE`로 끝났다.

이는 **평가 실행 검증 오류**다. 모델·검색 품질 실패로 집계하지 않는다. 원본 배열 순서를 바꾸거나 중계기를 수정하지 않았고, 실패 후 추가 요청·재실행은 하지 않았다. 전용 평가 Java 프로세스는 종료했다.
