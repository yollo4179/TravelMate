# LiLi 실행 결과와 설명의 일치 수정

기준: develop `61a4b391`. v3 c1 의미 검수에서 확인한 잘못된 안내 3건의 입력 경로와 프롬프트를 수정했다. 기존 실측 원본과 판정은 변경하지 않았다.

## 변경

| 기존 문제 | 변경 | 실제 모델 재검증 시 기대 결과 |
|---|---|---|
| 부산 질문·서울 필터에서 서울 카드를 해운대 주변이라고 소개 | 라우터는 명시 지역과 필터 충돌 시 앱 범위 변경을 안내하도록 수정. 추천 호출에는 카드 전체의 실제 지역·도시를 별도 전달 | 검색 전에는 현재 범위와 변경 방법을 안내. 검색이 실행돼도 서울 결과를 부산 추천으로 소개하지 않음 |
| 말로 계획 조건을 받으며 만들 수 있다고 약속 | 조건을 계속 말로 수집하라는 규칙 제거. 라우터 및 서버의 조건 누락 후속 안내 모두 앱 입력을 요구 | planningRequest가 없으면 말로 모든 조건을 받아도 생성 준비가 됐다고 하지 않고 앱 입력을 안내 |
| 세 번째 제외 후 다시 뜻을 묻고 '세 번째까지'로 바꿈 | 적용 필터와 반환 목록으로 제외 완료를 확인하고 이전 표시 목록의 정확한 순번을 전달 | 이전 제외를 유지하며 세 번째만 추가 제외한 사실을 완료형으로 설명. 다시 승인·뜻을 묻지 않음 |

`RecommendationExecutionFacts.execute()`는 공통 추천 작업에서 실행한다. `Facts`에 실제 지역 목록, 지역 미확인 카드 수, 제외 확인 상태와 정확한 순번을 담는다. 인용 원문이 없는 카드도 지역 메타데이터는 전달하지만 이름·설명은 다시 노출하지 않는다. 카드·원문·검색 조건은 변경하지 않는다.

제외 상태는 Enum으로 관리하고 프롬프트 표기도 `PromptVocabulary`에서 연결한다. 요청에 ID가 있다는 이유만으로 완료를 선언하지 않는다. 기존 제외가 필터에서 누락되거나 제외 장소가 결과에 나타나거나 검색이 실패하면 `UNVERIFIED`다. 정상적으로 완료된 빈 결과는 실패와 구분한다.

## 검증 범위

Java 관련 21개 검사: `LiliRouterTest` 13개, `RecommendationJobServiceTest` 4개, `RecommendationExecutionFactsTest` 4개.

- 추천 작업 → 실제 LLM 클라이언트 입력 조립 경로에서, 원문 없는 서울 카드의 지역과 세 번째 제외 완료 정보가 전달되는지 확인했다.
- 저장할 결과 카드가 바뀌지 않고 인용 불가 설명이 LLM에 다시 유입되지 않는지 확인했다.
- 이전 제외 필터 누락, 제외 장소 재등장, 필터 미관측, 검색 실패, 빈 결과, 지역 혼합·누락을 확인했다.
- 대화에 일정 조건이 있어도 구조화 입력이 없으면 계획을 접수하지 않고 앱 입력 안내용 사실을 후속 호출에 전달하는지 확인했다.

모델 응답은 mock이다. **이 검사는 입력·실행 상태 전달 및 서버 제어 검증이며, 모델의 실제 의미 정확성 개선을 입증하지 않는다.** 자연어 지역 충돌 판단과 문장 생성은 여전히 LLM이 수행한다. 새 유료 모델 호출·실제 검색·DB 변경·배포는 하지 않았다.

다음 실측은 위 3건을 우선 대상으로 하고 첫 대사와 최종 대사 모두 판정한다. 기존 37/42를 개선된 점수로 바꾸지 않는다. 비교 질문·호텔 검색 제안 2건은 이번 수정 범위에 포함하지 않았다.
