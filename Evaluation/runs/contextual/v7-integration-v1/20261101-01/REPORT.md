# v7 실제 PostgreSQL·Sonar·검색 검증

문서 버전: 2 · 실행·작성: 2026-11-01 · 설명 보강: 2026-11-01 · 구현 기준: `64bf5ef0` · 브랜치: `eval/contextual-v7-integration`

**SQL 통합은 통과했다. 실제 생성·검색에서는 위치 오류, Top-30 후보 손실, 활성 20개 상한 손실을 확인했다.**
문맥 품질·검색 품질이 개선됐다고 판정하지 않는다. 코드 기본 프롬프트 v2·기본 근거 수 1개를 유지하며 운영 DB는 변경하지 않았다.

## 실제 실행 범위

- 전용 내부 Docker 네트워크와 메모리 저장 PostgreSQL을 새로 만들었다. 운영 DB에 스키마·청크·벡터를 쓰지 않았다.
- PostgreSQL **17.10**, pgvector **0.8.5**에서 새 역할·trigger·실제 워커 SQL을 검증했다.
- 기존 `BAAI/bge-m3`, `BAAI/bge-reranker-v2-m3` CUDA 서비스를 그대로 호출했다. GPU는 RTX 4050 Laptop, sentence-transformers 6.2.0, torch 2.13.0+cu129다.
- Sonar는 고정 통제 원문 묶음 1건과 기존 P09 묶음 1건, 합계 **2회**만 호출했다. 실제 모델은 두 건 모두 `perplexity/sonar`, 공급자 상태는 completed다.
- 원문·장소 목록·fast·8192 출력 한도·tools=[]를 요청 전에 동결했다. 통제 자료는 합성이고 P09는 실제 보존 원문이다. 추가 웹 수집은 하지 않았다.
- 실제 검색은 고정 **12건**과 후속 원인 분리 진단 **2건**이다. 임베딩 HTTP 3회·58개 텍스트, 리랭킹 HTTP 12회다. 검색 근거는 2개, 기본 후보 30개, 장소별 활성 상한 20개를 고정했다.
- Spring→Kafka 메시지 전달이나 최종 답변 생성은 이번 경계가 아니다. 실제 워커의 후보·근거 SQL, 기존 모델의 임베딩과 리랭킹을 실행했다.

## PostgreSQL 통합

핵심 SQL 검사 6개를 먼저 통과했다.

- 한 청크를 A의 subject 슬롯·B의 relation_endpoint 슬롯으로 저장하고 다시 읽는다.
- B를 subject로 강제하거나 무관한 endpoint·지원하지 않는 역할을 직접 넣으면 trigger/제약이 거부한다.
- landscape는 A만, 목적지 B 조건은 A, 출발지 A 조건은 B를 반환한다. primary/supporting 필터와 두 근거 확장에도 같은 조건을 적용한다.
- 기존 subject 전용 역할 제약을 갱신하고 스키마를 재실행해도 기존 A 슬롯이 남는다.
- subject 없는 명확한 관계도 관계 전용으로 검색되며 경관 근거가 되지 않는다.
- 오래된 endpoint가 있으면 적용을 원자적으로 중단해 A의 부분 쓰기도 남기지 않는다.

최종 전체 회귀는 **110개 중 109개 통과·1개 skip**이다. 기존 DB 통합 검사도 실행했다.
평가 검사 9개도 통과했다. 남은 1개는 별도 환경 플래그가 필요한 기존 모델 통합 테스트이며, 실제 BGE 경로는 이번 14건으로 따로 실행했다.
초기 의존성·읽기 전용 출력 경로·합성 테스트 키 설정 오류의 실패 로그도 로컬에 보존했다. 최종 결과와 혼동하지 않는다.

## Sonar: 맞는 관계도 위치 때문에 손실

통제 문장:
“A공원은 야경이 아름답고, 관람 후 B공원으로 걸어갈 수 있다.”

모델은 A=subject, B=mentioned, content_kind=landscape, A→B=supporting과 정확한 이동 인용을 반환했다.
하지만 관계 인용의 **start=16**을 반환했고 실제 시작은 **15**다. end=35는 맞다.
현행 검증 v4가 이를 거부해 경관과 보조 이동을 담은 청크 전체가 색인 전에 제외됐다.
이는 API 인증·결제·SQL 오류가 아니라 **모델의 위치 계산과 현재 검증 계약에서 발생한 자료 손실**이다.

### 위치 오류의 실제 예시: 청크 연결 오류가 아님

**청크 번호·출처 ID를 잘못 연결하거나 원문을 잘못 잘라 만든 문제가 아니다.**
두 사례 모두 요청한 source_id와 청크 start/end에 해당하는 원문은 그대로 보존됐다.
잘못된 숫자는 Sonar가 응답의 `relations[].evidence`에 반환한 **청크 내부 이동 인용의 문자 위치**다.

위치는 0부터 세는 Unicode 문자 기준이고, end는 포함하지 않는다. `[15:35]`는 Python 원문 슬라이스 표기다.

| 이번 검증의 요청 순서 | 정상 보존된 청크 범위 | 모델이 반환한 관계 인용 범위 | 인용의 실제 범위 |
|---|---|---|---|
| 첫 번째 CONTROL | `[0:35]` | `[16:35]` | `[15:35]` |
| 두 번째 P09 | `[241:283]` | `[263:283]` | `[264:282]` |

첫 번째 CONTROL의 청크 전체는 다음과 같다.

```text
A공원은 야경이 아름답고, 관람 후 B공원으로 걸어갈 수 있다.
```

모델은 아래 인용 자체는 정확하게 썼다.

```json
{"evidence": {"start": 16, "end": 35, "quote": "관람 후 B공원으로 걸어갈 수 있다."}}
```

그러나 반환 위치로 자르면 첫 글자 ‘관’이 빠진다.

```python
source_text[16:35]  # "람 후 B공원으로 걸어갈 수 있다."
source_text[15:35]  # "관람 후 B공원으로 걸어갈 수 있다."
```

두 번째 P09에서도 인용은 `이제부터 계단으로 올라가시면 돼요`였지만,
모델의 `[263:283]`은 앞뒤 줄바꿈까지 포함한 `"\n이제부터 계단으로 올라가시면 돼요\n"`를 가리켰다.
정확히 인용과 일치하는 구간은 `[264:282]`다.

여기서 첫 번째·두 번째는 **이번 검증의 API 요청 순서**다. 웹 수집과 문맥 생성의 단계 번호가 아니다.
두 요청 모두 이미 저장된 원문으로 문맥·관계를 생성한 호출이며, 새 웹 수집은 하지 않았다.

현재 v7 계약은 모델에게 관계 인용뿐 아니라 숫자 start/end도 계산하도록 요구한다.
검증 코드는 그 숫자로 자른 원문이 quote와 다르면 관계가 포함된 청크 전체를 제외한다.
따라서 맞는 인용과 역할을 반환해도 숫자 계산 하나로 유효한 근거를 잃을 수 있다.
다음 수정 방향은 정확한 인용에서 서버가 위치를 계산하고, 중복 인용·불일치 인용은 보류하는 것이다.
이 문서 보강으로 실행 코드나 기존 응답을 수정한 것은 아니다.

다른 통제 문장의 핵심 계단 이동, B의 주차 시설, 공사로 막힌 이동 조건은 보존됐다.
공사 사례가 검색된다고 이동 가능으로 확정해서는 안 된다. 원문의 부정 조건을 함께 읽어야 한다.

| 생성 처리 | 통제 | P09 | 합계 |
|---|---:|---:|---:|
| 반환 구간 | 4 | 28 | 32 |
| 자동 검증 후보 | 3 | 15 | 18 |
| 자동 제외·보류 | 1 | 13 | 14 |
| 에이전트 검수 승인 | 3 | 8 | 11 |
| 유효 형식 후보 중 의미 검수 보류 | 0 | 7 | 7 |

P09는 위치 오류 외에도 엔티티 역할 불일치·같은 장소 ID의 중복 역할이 발생했다.
다른 공원 구간의 야경·테이블·관리·조경 등을 청담도로공원에 붙이는 문제도 남았다.
특히 P09-N015는 모델이 잘못된 subject를 반환했지만 중복 역할 검증에서 제외됐다.
이를 모델이 경관 소유 장소를 맞힌 것으로 세지 않는다. P09-N016 등 형식 검증을 통과한 잘못된 귀속도 검수에서 승인하지 않았다.
P09의 일부 진입·이동 설명에는 관계를 생성하지 않아 이동 검색에서 보류됐다.

검수는 버전을 아는 에이전트가 수행했다. 독립 사람·블라인드 평가가 아니다.

## 실제 검색: 세 단계의 손실을 구분

엄격한 v7 결과는 기존 처리 규칙 그대로 사용했다. 검색은 자동 후보 18개 전체가 아니라 에이전트 검수 승인 11개에서 시작했다.
별도 진단에서만 원문에 한 번 존재하는 정확한 인용의 위치를 15로 맞췄다.
원래 응답·실패 원인·검증 버전은 바꾸지 않았고, 이 감독 진단을 모델 자동 성공이나 서버 수정으로 세지 않는다.
[위치 진단](alignment-diagnostic.json)

스트레스 자료에는 같은 목적지 B를 가리키지만 도보 통행은 금지된 **합성 방해 사례 40개**를 고정해 넣었다.
운영 전체 자료의 대표 표본은 아니며, 제한에 의한 손실을 분리하는 통제 실험이다.

| 단계·질문 | 실제 관찰 |
|---|---|
| 엄격 처리의 A 경관·보조 이동 | 위치 검증에서 제외돼 색인·리랭킹까지 도달하지 못함 |
| 위치만 맞춘 A→B 보조 이동, B로 걸어갈 곳 | A에 활성화됐지만 벡터 순위 **41/41**, 기본 Top-30에서 제외 |
| 같은 벡터·근거를 41개 모두 리랭커에 전달 | A의 보조 이동 근거를 대표로 선택, **최종 1위** |
| 위치만 맞춘 A에서 B로 이동 | B에 연결 가능한 44개 중 기존 입력 순서에서 해당 근거가 44번째. 활성 20개 밖이라 검색 전 제외 |
| B의 20개 슬롯 중 하나에 해당 근거를 넣은 별도 진단 | 같은 방향 SQL·리랭커에서 **B 1위**로 정상 처리 |
| 핵심 계단 이동·실제 무료 주차 후기 | 필요한 근거가 리랭커에 도달했고 두 질문 모두 대표 근거와 장소 1위를 확인 |

후보 상한만 푼 진단은 실제 캐시 벡터와 같은 41개를 사용했다. 추가 임베딩·Sonar 호출은 없었다.
B 슬롯 진단도 상한 20개는 유지하고 합성 방해 근거 하나를 대상 근거로 교체했을 뿐이다.
이 결과는 **기본 Top-30이나 활성 정책을 늘리면 운영 품질이 개선된다는 입증이 아니다.**
후보 순위와 활성 선택에서 자료가 사라졌다는 원인 분리이며 운영 기본값은 변경하지 않았다.

추가로 P09 야경 질문에서는 실제 야경 근거가 없는 흙길 설명이 낮은 리랭킹 점수 0.02254로도 결과 1위에 남았다.
장소가 반환됐다는 것만으로 해당 질문을 뒷받침하는 유효 근거라고 보지 않는다. 이 수치를 정확도·신뢰 확률로 해석하지 않는다.
