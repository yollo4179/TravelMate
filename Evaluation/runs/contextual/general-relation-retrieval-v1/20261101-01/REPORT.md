# 이동 인용 벡터를 일반 의미 검색에 통합한 고정 비교

작성: 2026-11-01 · 기준 커밋: `1e646b33` · 작업 브랜치: `feat/contextual-general-relation-retrieval`

**관계 벡터 사용 모드에서 observation 필터가 없는 일반 의미 검색도 전체 청크와 이동 인용을 함께 검색하도록 구현했다.** 출발지·도착지를 알아야 관계 벡터 경로가 열리는 제한을 없앴다. 질문을 먼저 이동 의도로 분류하거나 예상 질문을 생성하는 단계는 추가하지 않았다.

같은 활성 자료로 실제 BGE 모델과 PostgreSQL에서 고정 질문 9개를 두 방식으로 비교했다. 이름 없는 도보 이동과 야경·이동 복합 질문에서 대상 A공원 1위를 확인했다. 이 질문들은 기존 일반 검색에서도 1위였으므로 **새로운 순위 개선으로 세지 않는다.** 새로 확인한 것은 일반 검색의 관계 표현 도달과 근거 범위 보존이다.

넓은 ‘연결된 곳’ 질문에서 사전 지정한 A는 변경 후에도 최종 28위였다. 활성 20개 밖에 있는 B의 보조 이동 근거도 여전히 제외된다. 일반 추천 품질 전체를 해결했다고 판정하지 않는다.

**문제와 변경**

기존 구현은 `use_relation_vectors`가 켜져 있어도 명시적 observation 이동 필터가 있어야 관계 벡터를 조회했다. 따라서 사용자가 일반 의미 검색에 이동 내용을 포함해도 저장해 둔 이동 인용 벡터를 사용하지 않았다.

새 검색 전략 레지스트리는 다음 중 하나를 선택한다.

| 조건 | 검색 표현과 범위 |
|---|---|
| 관계 벡터 모드·observation 없음 | subject의 전체 청크 + 활성 양쪽 endpoint의 해당 이동 인용 |
| 관계 벡터 모드·명시적 이동 조건 | 기존 방향·결과 endpoint·primary/supporting 조건을 만족하는 전체/관계 표현 |
| chunk-only 또는 명시적 경관·시설 조건 | 기존 subject 관찰 검색 |

일반 관계 검색에서는 출발지·도착지·관계 비중을 제한하지 않는다. 같은 질문 임베딩을 두 표현에서 사용한다. 관계가 여러 개이거나 표현이 많아도 점수를 합산하지 않고 장소별 최고 점수로 후보를 중복 제거한다. Top-30, 장소별 활성 청크 최대 20개, 기존 리랭킹 근거·쌍·토큰 예산을 유지했다.

**귀속과 복합 근거 보존**

합성 원문은 다음과 같다.

> A공원은 야경이 아름답고, 관람 후 B공원으로 걸어갈 수 있다.

- 경관의 주체는 A, B는 언급된 장소다. 이동은 A→B다.
- A의 subject 슬롯에서는 전체 청크와 이동 인용을 각각 검색 표현으로 사용할 수 있다.
- B의 relation_endpoint 슬롯에서는 A의 야경이 포함된 전체 청크 벡터를 사용하지 않는다. 해당 관계의 원문 이동 인용만 사용한다.
- 관계 표현으로 찾으면 출발지·도착지와 그 인용만 리랭커에 전달한다. 보존 원문과 place_refs는 그대로 두고 retrieval_scope/matched_relations로 사용 범위를 표시한다.
- 같은 청크의 전체 설명과 이동 인용이 근거 중복 제거에서 하나로 사라지지 않도록 키에 retrieval_path/relation_index를 포함했다. 두 관계도 각각 별도 근거로 유지한다.
- 후보 조회 후 같은 청크라도 선택된 표현이나 관계 순번이 바뀌면 근거 재검증에서 거부한다.

근거 수 기본값은 여전히 1이다. 이번 비교는 기존 선택 설정인 2를 사용했으며, 모든 질문에서 경관·이동 두 근거를 항상 보장하지는 않는다. 질문과 가까운 표현부터 기존 예산 안에서 선택한다.

끝점을 지정하지 않는 SQL에서는 JSON 조건을 사용하지 않는 경우에도 매개변수를 추가하던 문제가 발견됐다. 실제로 SQL이 참조하는 조건만 바인딩하도록 수정했고, 끝점 없는 movement 조건도 실제 DB에서 검증했다.

**고정 비교 조건**

| 항목 | 조건 |
|---|---|
| 자료 | 기존 승인 합성 통제 4개·실제 청크 8개와 합성 방해 40개 |
| 검수 | 기존 승인 재사용, 버전을 아는 에이전트 개발 검수. 블라인드 인간 평가 아님 |
| 활성 선택 | 기존과 동일, 장소별 최대 20개. B 쪽 보조 근거는 선택 순서 44번째로 계속 제외 |
| 장소 후보·리랭킹 근거 | 최대 30개·장소별 최대 2개 |
| 모델 | 기존 BGE-M3 / BGE-reranker-v2-m3, 기존 CUDA 서비스 |
| 기준군 | 1e646b33의 실제 후보·근거 SQL 메서드. 관계 모드는 켠 상태로 필터에 따른 기존 경로 사용 |
| 변경군 | 같은 DB·벡터·자료에서 일반 의미 검색 통합 SQL 사용 |
| 실행 수 | 질문 9개 × 검색 방식 2개 = 18개 |

기존 원본의 publication 해시를 실행 전후 확인했다. 기준 SQL 파일 해시와 질문·활성 목록·추가 임베딩 입력은 실행 전에 동결했다. 새 자료 생성·추가 의미 승인·운영 DB 반영은 하지 않았다.

복합 질문에서 변경군 A의 최종 점수는 약 0.8882였고 전체 청크가 대표 근거였다. 추가 근거에는 같은 원문의 A→B 이동 인용이 남았다. 리랭킹 점수는 사실 확률이나 조건 충족 확률이 아니다.

‘연결된 곳’은 도보·거리 조건을 명시하지 않는다. 차량 연결을 설명하는 방해 자료를 이 질문의 오답으로 일괄 판정할 수 없다. 표의 A는 사전 지정한 진단 대상이며, 이 질문에는 별도 의미 평가가 필요하다. 낮은 점수의 결과를 어떻게 보류할지도 이번 범위에서 바꾸지 않았다.

과거 ‘명시적 도착지·supporting’ 조건에서의 Top-30 손실을 일반 검색에서도 발생한다고 단정해서는 안 된다. 이번 일반 검색 비교에서는 A가 기존부터 후보 1위였다. 서로 다른 필터의 후보 집합과 순위를 같은 실패로 취급하지 않는다.

**검사와 비용**

- 새 검사 13개: 단위 5개·실제 PostgreSQL 8개. 필터 없는 양쪽 endpoint 검색, 목적지에 경관 점수 전이 방지, 선택 필터와 지역·거리·제외 장소 조건, 비활성/오래된 장소 제외, 후보 30개·근거 예산, 같은 청크의 두 관계, 표현 변경 감지를 확인했다.
- 서버 전체 157개 중 **156개 통과·기존 모델 플래그 검사 1개 건너뜀**, 실패·오류 0개. 실제 BGE는 위 고정 비교에서 별도 호출했다. [검사 결과](tests.json)
- 초기 검사에서 새 SQL의 미사용 바인딩 오류와 검증 컨테이너의 읽기 전용 아카이브 경로 오류를 확인했다. SQL을 수정하고 아카이브 경로를 폐기용 /tmp로 지정한 뒤 최종 회귀를 통과했다.
- 기존 청크·관계 벡터를 재사용했다. 신규 고유 질문 4개를 /embed 1회로 계산했고 두 검색 방식에서 같은 질문 벡터를 사용했다.
- 저장된 동일 질문·텍스트 점수는 재사용했다. 새 리랭킹은 12회·351개 입력이었다. 같은 입력은 다시 호출하지 않았다.
- 유료 Perplexity·Sonar 호출 0회, 운영 DB 쓰기 0회, 운영 서비스 재시작 0회다.

일반 검색 6개에서 기준군의 리랭킹 입력은 질문당 31~32개였고 변경군은 60개였다. 장소별 근거 상한은 같지만 표현이 늘면서 실제 계산량은 증가했다. 전체 지연·대규모 SQL 비용·동시성 성능은 측정하지 않았으며 속도 개선을 주장하지 않는다.

**사용 범위와 남은 작업**

기존 선택 설정 `CONTEXTUAL_RELATION_RETRIEVAL=chunk-and-relation-v1`에서 필터 없는 일반 검색 통합이 작동한다. `chunk-only` 기본값과 운영 설정은 유지했다. 기존 청크에 관계 벡터가 없으면 검수된 대상의 재색인이 필요하다.

이동 의도를 먼저 분류하는 기능, 예상 질문 벡터, 활성 20개 정책 변경, 잘못된 장소·주체 귀속 수정, 최종 자연어 답변 생성은 추가하지 않았다. 현재 통합은 검색 워커의 후보·근거 조회와 결과 근거 보존까지다. Spring/UI에서 해당 근거를 표시하고 설명하는 최종 사용자 흐름 전체의 검증은 아니다.

관계 검색 경로가 열리는 것과 질문에 맞는 추천 순위·조건 충족이 보장되는 것은 별개다. 이 기록은 일반 의미 검색에서도 기존 관계 표현을 사용할 수 있게 된 구현과 제한된 실측 결과를 남긴다.
