# 장소별 근거 1·2·3개 비교 실험 A

문서 버전: 1 · 실행·작성: 2026-10-31 · 구현 기준: `4ed97294`의 후속 작업

**근거 2개에서 필요한 원문 전달과 대표 근거 선택이 개선됐다. 근거 3개는 추가 품질 이득이 없었다.**
생성 문맥 오류가 남아 있고 이 표본은 한 장소뿐이므로 서비스 기본값은 1개로 유지한다.

## 구현

- 장소별 활성 subject 청크 최대 20개, 후보 장소 30개, 반환 장소 20개를 유지했다.
- `CONTEXTUAL_RERANK_EVIDENCE_PER_PLACE`에 1·2·3을 설정할 수 있다. 기본값 1은 기존 단일 근거 경로다.
- 복수 근거는 기존 후보 장소 안에서만 추가 조회한다. 장소별 chunk/context 중복을 제거하고 문맥+원문 쌍을 각각 같은 리랭커에 전달한다.
- 장소 점수는 최고 근거 점수다. 합산하지 않고 장소를 중복 반환하지 않는다. 동점은 기존 후보 순서를 따른다.
- `description`은 최고 점수 근거이며 `evidence_chunks`는 점수 순 근거 목록이다. 각 근거의 원문·offset·역할·버전·출처와 개별 점수를 보존한다.
- 복수 근거 경로에 요청당 90쌍·32,768 유효 입력 토큰 예산을 적용했다. 초과하면 모델 호출 전에 실패하며 근거를 몰래 줄이지 않는다.
- 원본 버전·대표 활성 근거가 후보 조회 후 바뀌면 실패한다. `SEMANTIC_ONLY`는 추가 근거 조회를 하지 않는다.

## 비교 조건

기존 `v1_local`·v2 비교의 **보존 v2만** 사용했다. 프롬프트·분할·원문·질문을 바꾸지 않았다.
원문 22구간·입력 9묶음은 각각 따로 활성화했다. 모든 출처를 한 장소에 함께 올린 운영 실험이 아니다.
같은 449개 장소 스냅샷과 같은 쿼리 벡터를 사용했고, 질문별 장소 후보 30개와 최초 대표 근거가 모든 비교에서 같음을 검사했다.

26문항 × 근거 수 3가지 × 반복 3회 = **234건**이다. 각 문항에서 실행 순서를 회전했다.
첫 실행의 리랭커 예열 3회는 집계에서 제외했다. 반복별 장소 순위·대표 구간·반환 구간 결과는 모두 같았다.
단일 근거 78건은 앞 실측의 v2 장소 순위·선택 구간과 모두 일치했다.

실제 모델은 BGE-M3와 BGE reranker v2 m3, GPU는 RTX 4050 Laptop, 리랭킹은 batch 8·autocast_fp16이다.
이미 실행 중인 서버의 모델을 HTTP로 재사용하고 최신 추천 작업자 코드는 별도 프로세스에서 실행했다.
모델을 두 개 더 올리거나 운영 서비스를 재배포하지 않았다.

이 질문은 에이전트가 원문에서 만든 탐색 표본이다. 독립 시험셋·사람의 블라인드 검수가 아니다.
다른 448개 장소의 관련성을 모두 판정한 것이 아니므로 아래 수치를 전체 검색 Precision·Recall로 표현하지 않는다.

**보조 근거까지 포함한 반환 노출은 1→2→3문항으로 늘었다.**
근거를 늘리면 잘못 생성된 문맥도 함께 전달될 수 있다. 복수 근거가 사실 검증을 대신하지 않는다.
원문 라벨로 구간 선택을 검사한 결과이지 생성 문맥 전체의 의미 정확도를 다시 독립 평가한 결과도 아니다.

나머지 4개 문항은 잘못된 전제·혼합 장소를 살피는 진단 질문이다. 답변을 생성하지 않았으므로 답변 환각률은 집계하지 않았다.

## 지연·토큰·GPU

각 설정당 26문항 × 3회 = 78표본이다. p50/p95는 가까운 순위 표본으로 계산했다.
쿼리 벡터를 재사용했으므로 아래 코어 지연은 실제 쿼리 임베딩 HTTP 호출과 Spring/Kafka 전달을 포함하지 않는다.
DB 조회·추가 근거 조회·작업자 전달·모델 HTTP 왕복과 복수 근거 토큰 검사는 포함한다.
결과 파일 쓰기와 사후 채점은 제외했다. 서버 내부 큐 대기와 순수 GPU 추론 시간은 HTTP 왕복에서 분리하지 못했다.

| 지표 | 1개 | 2개 | 3개 |
|---|---:|---:|---:|
| 코어 지연 p50 / p95 | 420 / 739ms | 444 / 783ms | 449 / 852ms |
| 리랭커 HTTP p50 / p95 | 410 / 732ms | 422 / 769ms | 428 / 837ms |
| DB 합계 p50 / p95 | 5.9 / 10.9ms | 7.3 / 14.5ms | 7.0 / 14.5ms |
| 실제 쌍 수 범위 | 30 | 30~31 | 30~32 |
| 실제 총 토큰 범위 | 5,043~7,375 | 5,279~7,483 | 5,279~7,526 |
| 관측된 장치 전체 메모리 최고값 | 4,755MiB | 4,755MiB | 4,755MiB |

한 장소에만 보강 청크가 있으므로 실제 품질 실험은 60·90쌍 부하가 아니다.
GPU 값은 nvidia-smi로 100ms마다 관측한 **공유 장치 전체 사용량**이다.
기존 모델과 캐시도 포함하므로 요청별 추가 메모리나 PyTorch 최대 할당량으로 해석하지 않는다.
동일 최고값이 나왔다고 근거 증가의 메모리 비용이 0이라고 결론내리지 않는다.

별도 부하 실험에서는 단일 근거 기준 후보 중 총 토큰이 가장 긴 Q17의 실제 후보 텍스트를 반복했다.
장소·근거가 실제로 90개 검색됐다는 실험이 아니라 모델 입력 부하만 확인한 것이다.
크기마다 예열 1회·측정 3회이며 모든 측정이 완료됐다.

| 입력 쌍 수 | 총 토큰 | 배치 수 | HTTP p50 / 최대 |
|---|---:|---:|---:|
| 30 | 7,375 | 4 | 440 / 444ms |
| 60 | 14,750 | 8 | 747 / 762ms |
| 90 | 22,125 | 12 | 1,062 / 1,103ms |

부하 실험의 최대 쌍 길이는 573토큰이다. 모델 창 8,192토큰까지 긴 입력·동시 요청 부하를 검증한 것은 아니다.
3표본의 p95를 운영 SLA처럼 해석하지 않도록 표에는 최대값을 적었다.
