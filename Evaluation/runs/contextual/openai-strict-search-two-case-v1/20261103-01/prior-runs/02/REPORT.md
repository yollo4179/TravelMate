# OpenAI strict 기존 2문항 배치 결과

두 문항을 각 1회 실행했고 모두 `COMPLETED / PLACES`로 종료했다. 도구 선택은 두 문항 모두 `search_places`였으나, 두 번째 문항에서 모델이 잘못된 분류 필터를 추가해 검색 결과가 비었다. 자동 수정·재검색·재실행은 하지 않았고 배치 후 전용 Java 프로세스를 종료했다.

이전 실행 `openai-strict-live-20261103-01`의 `COUNT_UNAVAILABLE`은 기록용 중계기의 본문 처리 오류다. `EVALUATION_INFRASTRUCTURE / NOT_EVALUATED`로 분류하고 모델 품질 집계에서 제외한다. 이전 원본 결과는 변경하지 않았고 `../prior-run-classification.json`에 분류와 원본 해시를 보존했다.

## 최소 변경과 오프라인 검증

중계기의 `Content-Length` 전용 본문 읽기를 Java 클라이언트가 실제 사용하는 chunked 본문도 읽도록 수정했다. 본문은 JSON 해석 전에 저장한다. 기존 클라이언트의 예산 예약·토큰 가드와 중계기의 호출 상한·오류 후 중단 장치는 유지했다. 애플리케이션 소스와 JAR는 이전 가드 검증 후의 해시와 동일하다.

실제 `OpenAiLlmClient`, `LlmHttpClients`, 원래 시스템 프롬프트·도구 정의·기존 두 문항 입력을 사용해 외부 연결 없이 로컬 수신처로 전송했다. 계산·추론 요청 4개 모두 chunked 방식이었으며 기록 본문과 수신 본문이 바이트 단위로 일치했다. 추론 본문은 클라이언트 가드가 기록한 SHA-256과도 일치했다. 오프라인 응답은 전송 확인용 자료이며 품질·실제 사용량에 합산하지 않는다. 후속 검색 근거를 포함한 실제 두 번째 모델 요청은 본 실행에서 기록한 본문 해시로 검증했다.

검증 자료: `../offline/verification.json`, `recorder-change.patch`. 전송 수정 외의 기능 개발은 수행하지 않았다.

## 도구 선택·인자·근거 설명

### PLR-TM-palaces-01 — 창경궁을 찾아줘.

- `search_places`를 1회 선택했다. `query="창경궁"`, `region="서울"`, `limit=5`, 나머지 선택 필터는 null 또는 빈 배열이다. 장소명과 지역 범위를 보존했다.
- 검색 결과: 창경궁(378), 창경궁 홍화문(379), 율곡로(339), 창덕궁 낙선재(380), 창덕궁 인정문(381). 창경궁이 1위였다.
- 최종 설명은 창경궁을 식별하고 창덕궁과의 관계 및 복원 내용을 설명했다. 인용 2개 모두 해당 장소에 전달된 원문·근거 ID·출처 ID와 일치하며 인용문은 원문의 정확한 연속 부분이다.
- 모델의 원래 인자와 서버에 전달한 인자는 동일하다. 수정하거나 검색어를 보완하지 않았다.

### PLR-TM-palaces-03 — 종로의 조선 왕실 가족 생활 공간

- `search_places`를 1회 선택했다. `query="조선 왕실 가족이 생활했던 궁 또는 거처"`, `region="서울"`, `city="종로"`, `limit=10`이었다.
- 모델이 `category="궁"`을 추가했다. 동결 자료의 정답 장소인 창경궁(378), 서울 운현궁(208), 창덕궁 낙선재(380), 건청궁(10)의 분류는 `관광지`다. 이 인자는 요청 의도를 올바른 분류 값으로 표현하지 못했다.
- 적용된 검색 조건에도 `category="궁"`이 그대로 남았으며 검색 추적에 후보·반환 수가 모두 0으로 기록됐다. 잘못 추가한 필터가 빈 결과를 만든 것으로 판단한다. 반사실 재검색은 하지 않았다.
- 최종 응답은 검색되지 않았다고 설명하고 재검색 의사를 물었다. 빈 도구 결과를 장소 부재로 단정하지는 않았지만, 요청한 거처의 근거 설명과 인용은 제공하지 못했다.
- 스키마와 실행 상태는 성공이지만 인자 의미의 정확도에 문제가 있다. 인자나 기능을 수정하지 않았다.

위 내용은 실제 기록을 읽은 관찰이다. 별도 모델 judge와 의미 점수 산출은 수행하지 않았다.
