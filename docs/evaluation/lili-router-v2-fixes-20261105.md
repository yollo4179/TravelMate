### 수정으로 새로 생긴 문제와 재수정

- **exclude-shown: 카드 10개가 보이는데 "후보가 비어 있어", "안 잡혔어"라고 말함 (fx2·fx3·fx5).**
  LiLi가 받는 후보 목록이 비어 있으니 결과가 없다고 해석했다. `73129042`에서 화면에 보이는 카드 수(`shownCardCount`)를 함께 주고 "결과 없음"으로 말하지 않게 했다.
- **계획 설명에 입력 필드 이름 노출 (fx3: "requiredStops를 정확히 한 번 포함").** `73129042`에서 계획 프롬프트로 막고, 채점기가 계획 제목·설명·핀 설명의 camelCase 필드 이름도 잡게 했다. 저장된 v2 실행 전체를 다시 검사해 이 1건만 걸렸다.
- **계획 대사의 "바로 다듬어줄게" (fx1·fx4·fx5).** 초안 수정 기능은 없다. `73129042`에서 금지했다.

### 재수정 확인 (fy, fz)

- fy1~fy5(`73129042`, exclude-shown·PLAN-create만 5회)
  - exclude-shown: 5회 모두 "카드에 다른 곳들이 보인다"고 말했다. "후보가 없다"는 0회.
  - PLAN-create: 4/5 완성, 모두 창경궁 60분 1곳. 필드 이름 노출과 초안 수정 약속은 0회.
  - fy2 실패: 모델이 "창경궁은 창덕궁과 경계 없이"를 "창경궁은 경계 없이"로 낱말을 빼고 인용했다. 의미가 바뀌는 변경이라 검사기가 맞게 거부했다. 같은 초안의 다른 인용은 한자 병기만 뺀 것이라 허용됐다.
- fz1~fz5(`bcb05c87`, exclude-first만 5회)
  - 4/5는 "목록이 보이는 화면에서 다시 말하기"와 "새로 찾기"만 제시했다.
  - fz1은 선택지 하나가 "첫 번째를 빼고 새로 검색하기"였다. 새 검색에서는 뺄 대상을 알 수 없어 여전히 쓸 수 없는 선택지다.
- 계획 완성: 수정 전 var 3/5 → fx 5/5, fy 4/5. 남은 실패 유형은 모델이 인용을 원문과 다르게 옮기는 것 하나다.

- **라우터 토큰 계산 요청은 이번 평가 설정에서 없어지지 않았다.**
  - 대화 단계 호출 55회 중 50회(라우터)가 여전히 공급자 계산을 썼고, 후속 대사 5회만 바이트 상한을 썼다.
  - 이유: 평가 정책의 문맥 한도가 8,192(입력 6,656)인데, 가능한 일 목록을 넣은 뒤 라우터 요청이 약 7.3KB가 됐다. 한국어는 글자당 3바이트라 바이트 상한이 한도를 넘는다.
  - 바이트 상한을 쓴 5회는 모두 실제 사용량을 넘지 않았다(`countCoversUsage=true`).
  - 실제 모델의 문맥 한도로 운영하면 라우터도 바이트 상한을 쓴다. 평가에서 효과를 재려면 평가 문맥 한도와 비용 상한을 올려야 한다(아래 결정 필요).
- 첫 대사 지연이 조금 줄었지만 라우터 계산 요청 제거 덕은 아니다(라우터는 여전히 계산 요청을 썼다). 원인을 나누어 확인하지 않았다.
- **작업 대기는 여전히 26~61초(중앙값)다.** 이번에는 Kafka 파티션 할당 뒤에 시작했고(fx1: 기동 3초 만에 할당), 그래도 길었다. 따라서 원인은 Kafka 합류가 아니라, 검색 요청을 보낸 뒤 결과가 돌아오기까지의 구간이다. 검색 작업자(GPU 6.1GB 중 5.8GB 사용)를 따로 조사해야 한다.
