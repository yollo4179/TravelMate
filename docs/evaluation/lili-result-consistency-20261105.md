`RecommendationExecutionFacts.execute()`는 공통 추천 작업에서 실행한다. `Facts`에 실제 지역 목록, 지역 미확인 카드 수, 제외 확인 상태와 정확한 순번을 담는다. 인용 원문이 없는 카드도 지역 메타데이터는 전달하지만 이름·설명은 다시 노출하지 않는다. 카드·원문·검색 조건은 변경하지 않는다.

제외 상태는 Enum으로 관리하고 프롬프트 표기도 `PromptVocabulary`에서 연결한다. 요청에 ID가 있다는 이유만으로 완료를 선언하지 않는다. 기존 제외가 필터에서 누락되거나 제외 장소가 결과에 나타나거나 검색이 실패하면 `UNVERIFIED`다. 정상적으로 완료된 빈 결과는 실패와 구분한다.

| 없는 자료: 확인·검색해 주겠다는 제안 | 운영시간 6회, 주차 6회, 휠체어 3회 | 운영시간 1/6, 주차 3/6, 휠체어 2/3. "주차 가능한 관광지로 다시 찾아볼까?", "휠체어 이용에 도움 될 만한 곳을 찾아보거나" 등. 데이터에 이런 항목이 없다. c1·r1은 0/4였다 |
| 비교 질문 | 6회 | 검색하지 않음 4/5(반복분), 검색어에 비교 대상 없음 2/6. 이번 수정 범위 밖이고 c1과 같다 |
| 인용 이어 붙이기로 대답 전체 버림 | 왕족 거처 6회 | **3/6.** 세 번 모두 같은 인용("창경궁은" + 떨어진 구절)이다 |

### 판단

- **서버가 사실을 코드로 넘긴 부분은 고쳐졌다.** 카드의 실제 지역, 제외 완료 상태, 일정 조건이 앱 입력으로 오지 않았다는 사실이 그렇다. 새로운 말에서도 같았다(보류 문항).
- **프롬프트 규칙만으로 고친 부분은 부작용을 냈다.**
  - 라우터 지역 충돌 규칙: 해수욕장 문항에서 검색을 건너뛰게 했다(3/6).
  - 추천의 "범위를 바꿔 요청하라" 규칙: 데이터에 없는 지역으로 안내하게 했다(12/12).
  - "세 번째도 빼 줘"의 검색어 누락(3/6)도 이번 커밋 뒤에만 나왔다. 원인은 확인하지 못했다.
- **남은 틀린 안내는 대부분 한 가지 원인이다.** LiLi가 데이터에 무엇이 있는지(지역은 서울뿐, 분류는 관광지뿐, 운영시간·주차·편의시설 항목 없음) 모른다. 그래서 다른 지역 검색, 주차 검색, 휠체어 검색을 제안한다. 사례마다 금지 규칙을 붙이지 말고, 서버가 데이터 범위와 항목을 코드로 넘겨야 한다.

### 다음 수정 (층별)

| 순서 | 수정 | 층 | 고치는 것 |
|---|---|---|---|
| 1 | 서버가 데이터 범위(DB의 지역·분류 목록)와 장소 자료에 있는 항목을 사실로 넘긴다. "범위를 바꿔 요청하라" 규칙은 "데이터에 있는 범위 안에서만 제안한다"로 바꾼다 | 코드 사실 | 다른 지역 안내 12건, 해수욕장 지역 약속, 없는 자료 검색 제안 |
| 2 | 라우터 지역 충돌 규칙을 뺀다. 1번의 사실로 대신한다 | 라우팅 규칙 | 해수욕장 검색 건너뜀 |
| 3 | 검색 분기에 검색어가 없고 제외 순번만 있으면, 서버가 이전 결과의 검색어를 이어 쓴다 | 코드 | "세 번째도 빼 줘" 대답 실패 |
| 4 | 추천 인용 검증을 계획과 같게 바꿀지 결정한다(틀린 인용만 빼고 대답은 저장) | 검증 정책 | 왕족 거처 대답 버림 |
| 5 | 일정 생성 실패 때 LiLi 반응(진행 중) | 실패 뒤 응답 | `V3-D-plan-too-short` 등 |

1~3을 함께 바꾸고 v3 42문항과 보류 6문항을 다시 돌린다. 보류 문항 문장은 프롬프트 규칙이나 예시에 넣지 않는다.

## 일정 생성 실패 때 LiLi 반응 (2026-11-05)

일정 작업이 실패하면 지금까지는 서버 문구(합니다체)만 작업에 남았다. 사용자가 작업 상태를 물을 때만 LiLi가 "작업이 실패했다"는 한 줄짜리 사실로 그 문구를 다시 전했다. 서버가 실제로 무엇을 찾아봤는지는 LiLi에게 전달되지 않았다.

**바꾼 것**
- 실패 종류는 서버 코드가 정한다(`PlanFailure`).

  | 종류 | 반응 |
  |---|---|
  | 범위 안에서 장소를 찾지 못함 | LiLi |
  | 서버 규칙으로 거절(시간 초과 등, 규칙의 사유 그대로) | LiLi |
  | 초안을 읽지 못함 | LiLi |
  | 모델 호출 실패 | 미리 써 둔 LiLi 문구 |
  | 대기열 초과 | 미리 써 둔 LiLi 문구 |
  | 그 밖의 원인 | 미리 써 둔 LiLi 문구 |

- 작업이 실패하면 그 자리에서 반응을 한 번 만들어 작업에 함께 저장한다(`planning_jobs.failure_dialogue`, 이전 스크립트 `Docker/migrations/20261105c_planning_job_failure_dialogue.sql`).
  - LiLi 반응은 후속 대사 프롬프트(페르소나 포함)에 실패 상황과 사용자에게 보여 줄 사유를 넣어 만든다.
  - 모델 호출 실패에는 모델을 다시 부르지 않는다.
  - 반응을 만들지 못해도 작업은 FAILED로 끝나고, 오류 문구는 그대로 남는다.
- 반응 전략은 반응 종류마다 정확히 하나가 고르도록 등록한다(`LiliPlanFailureReaction`, `PreparedLinePlanFailureReaction`).
- 사용자가 작업 상태를 물으면 저장된 반응을 그대로 보여 준다. 모델을 한 번 더 부르지 않는다. 반응이 없는 예전 작업은 기존처럼 후속 대사로 전한다.
- 채점기: 실패 작업에 반응이 있는지(`plan_failure_reaction`) 검사한다. 반응 대사도 내부 용어 검사와 의미 검수(`final_text`)에 넣는다.

**확인**
- 서버 테스트 487건 중 482건이 통과했다. 실패 5건은 개발용 임베딩 서버(8000번)가 필요한 기존 테스트다. 평가용 검색 서버만 켜 두었기 때문이다.
- 평가기 테스트 222건 중 221건이 통과했다. 실패 1건은 기존부터 실패하던 `test_migration`이다.
- 실측 `20261105-lili-v3-pf2`(2문항): 둘 다 통과했다.
  - `V3-D-plan-too-short`: LiLi 반응이 "미안해, 이번 초안은 저장하지 못했어. 체류시간이랑 이동 여유를 합치면 여행 가능 시간을 넘어서서 그래."였다.
  - `CONV-PLAN-create`는 그대로 성공했다.
- 그 전 실행 `-pf1`은 이전 스크립트를 같은 컨테이너의 다른 DB(`travelmate_b_spring`)에 적용한 상태에서 돌았다.
  - 작업 조회가 없는 칸을 읽다가 실패해 두 문항 모두 도구 실패로 끝났다. 기록은 그대로 둔다.
  - 그때 멈춘 작업 2개는 다음 서버 시작 때 기존 복구 로직이 FAILED로 정리했다.
  - `travelmate_b_spring`에 추가한 빈 칸은 같은 이전 스크립트의 결과라 그대로 두었다.

**남은 점**
- 반응이 실패 사유만 전하고 다음에 할 일(끝나는 시간 늘리기 등)은 말하지 않았다. 1회 관찰이다.
- 개발용 스택은 `Docker/stack-up.sh`를 다시 실행하면 기존 DB에도 이 칸이 추가된다.
