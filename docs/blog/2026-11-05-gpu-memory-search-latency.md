# GPU 메모리가 넘쳐 검색이 10배 느려졌다: 리랭커 설정 두 줄로 검색 왕복 33.9초 → 3.0초

> 블로그 초안. 같은 10문항·같은 모델·같은 평가 인프라에서 설정 두 개만 바꾸기 전과 후를 비교한 기록이다.
> 수치는 평가 실행 기록과 서버 관측 이벤트에서 뽑았다. 메모리 구성 중 계산 중간값(리랭크 activation) 크기는 모델 구조로 계산한 추정치다.

## 요약

| 항목 | 조치 전 | 조치 후 |
|---|---|---|
| 검색 왕복 중앙값 (palaces-01 / palaces-03 / exclude-shown) | 33.9 / 33.4 / 23.9초 | **3.0 / 3.1 / 2.9초** |
| 추천 작업 대기 중앙값 | 26.4~38.7초 | **6.1~8.1초** |
| 계획 작업 대기 중앙값 | 30.4초 (최대 60.8초) | **9.2초** |
| GPU 전용 메모리 / 시스템 RAM으로 밀려난 양 | 5,821MB / 3,200MB | 4,967MB / 78MB |
| 평가 반복 1회 소요 | 약 3.5분 | 약 1.5분 |
| 자동 검사 | 50/50 | 50/50 |

바꾼 것은 리랭커 설정 두 개다. 묶음 크기 32 → 8, 입력 길이 상한 8,192 → 1,024토큰. 지금 데이터에서는 검색 점수가 바뀌지 않는 범위다.

## 1. 문제 정의

### 증상

LiLi 라우터를 도입한 뒤 첫 대사는 약 2초 만에 나왔다. 하지만 실제 결과(추천 카드와 설명, 일정 초안)는 작업으로 따로 처리되고, 사용자는 그 결과를 30~60초 기다려야 했다.

- 추천 작업 대기: 중앙값 26.4~38.7초 (cx1~cx5)
- 계획 작업 대기: 중앙값 30.4초, 최대 60.8초
- 평가도 느렸다. 10문항 반복 1회에 약 3.5분이 걸렸다.

### 무엇이 문제인가

- 사용자 경험: "찾아볼게"라고 말한 뒤 30초 넘게 아무것도 나오지 않는다.
- 측정: 이전 실측 r3에서는 같은 작업이 8~26초였다. 실행마다 대기 시간이 크게 달라, 응답 속도를 비교 지표로 쓸 수 없었다.

## 2. 원인 찾기: 가설과 검증

```mermaid
flowchart LR
    A[사용자 요청] --> B[Spring: 작업 접수]
    B --> C[Kafka 검색 요청]
    C --> D[검색 작업자<br/>임베딩 → 벡터 검색 → 리랭크 30개]
    D --> E[Kafka 검색 결과]
    E --> F[Spring: LiLi 설명 생성<br/>OpenAI 약 2~3초]
    F --> G[작업 완료]
```

### 가설 1. 서버 재시작 직후 Kafka 소비자 그룹 합류가 늦다 → 주원인 아님

- 반복 실측은 매번 서버를 강제 종료하고 다시 띄웠다. 죽은 소비자가 세션 만료 전까지 그룹에 남으면, 새 소비자의 파티션 할당이 늦어진다.
- 관측: 파티션 할당까지 var5는 32초, r3는 18초가 걸렸다.
- 검증: 파티션 할당을 확인한 뒤 실측을 시작했다(fx). fx1은 기동 3초 만에 할당됐는데도 작업 대기가 26~38초였다. 서버가 뜬 지 몇 분 지난 8번째 문항도 27초를 기다렸다.

### 가설 2. 검색 작업자의 대기열 폴링이 느리다 → 아님

- 작업자의 요청 처리 루프는 0.25초, 결과 발행 루프는 0.5초 간격이었다.

### 측정 1. 작업 대기를 구간별로 나눴다

Spring이 기록하는 검색 왕복 시간(`EVIDENCE_PREPARATION.durationMs`)과 작업 실행 시간을 분리했다(cx1~cx5).

| 문항 | 검색 왕복 (5회) | 검색 후 실행 |
|---|---|---|
| palaces-01 | 33.9, 33.8, 33.3, 34.0, 34.2초 | 중앙 3.1초 |
| palaces-03 | 33.4, 33.7, 33.4, 51.6, 33.0초 | 중앙 2.9초 |
| exclude-shown | 24.2, 23.4, 23.7, 23.9, 24.2초 | 중앙 2.0초 |

- 대기의 거의 전부가 **검색 자체**였다.
- 같은 질의는 매번 같은 후보 30개를 리랭크하는데, 걸린 시간도 실행마다 거의 같았다. 기다림(대기열)이 아니라 **계산이 느린 것**이다.

### 측정 2. GPU 메모리

- `nvidia-smi`: 5,815MB / 6,141MB 사용. 프로세스별 사용량은 Windows(WDDM)에서 `N/A`로 나와 알 수 없었다.
- Windows 성능 카운터(`\GPU Process Memory(*)`)로 다시 쟀다.

| 프로세스 | GPU 전용 메모리 | 공유 메모리 |
|---|---|---|
| `vmwp` (Docker Desktop의 WSL2 VM) | 5,821MB | **3,200MB** |

- **전용 메모리 6.1GB를 넘친 3.2GB가 시스템 RAM으로 밀려나 있었다.** Windows는 넘친 GPU 메모리를 시스템 RAM으로 옮겨 계속 실행한다. 그래서 오류 없이 계산만 크게 느려진다.
- Docker에서 GPU를 쓰는 컨테이너는 평가 검색 서버 `tm-b-eval-search` 하나였고, 그 안의 프로세스도 하나였다. 개발용 임베딩 컨테이너는 멈춰 있었다.
- Docker 밖의 GPU 사용자(Epic Games 런처와 오버레이)는 메모리를 거의 쓰지 않았다. 종료해도 사용량이 그대로였다.

### 측정 3. 메모리는 어디에 쓰였나

| 구성 | 크기 | 근거 |
|---|---|---|
| 임베딩 모델 `BAAI/bge-m3` 가중치 | 2,166MB | 모델 파일 크기, fp32 |
| 리랭커 `BAAI/bge-reranker-v2-m3` 가중치 | 2,166MB | 모델 파일 크기, fp32 |
| CUDA 기본 메모리 | 약 0.3~0.5GB | 일반값 |
| 리랭크 계산 중간값 | 약 2.5~3GB (추정) | 아래 계산 |

리랭커 설정은 다음과 같았다.

- 후보 30개를 **한 묶음(최대 32개)**으로 계산하고, 묶음 전체를 가장 긴 후보 길이에 맞춰 채운다.
- 입력 길이 상한이 따로 없어 모델 기본값 **8,192토큰**이 적용됐다.
- 실제 입력(질의 + 장소 설명, 장소 26곳)은 80~817토큰, 중앙 287토큰이었다.

attention 점수 표 하나의 크기는 묶음 30 × 헤드 16 × 817² × 4바이트로, 층마다 약 1.2GB다. softmax 결과와 FFN 중간값까지 합치면, 한 묶음 계산의 최고점은 2.5~3GB다.
PyTorch는 한 번 할당한 GPU 메모리를 반환하지 않고 캐시로 들고 있으므로, 이 최고점이 그대로 남는다.

합계 7~8GB가 6.1GB GPU에 들어가지 않아 일부가 시스템 RAM으로 밀려났다.

## 3. 해결

### 고려한 방법

| 방법 | 메모리 효과 | 검색 점수 영향 | 결정 |
|---|---|---|---|
| 리랭커 묶음 크기 32 → 8 | 계산 중간값 약 1/4 | 없음 | 적용 |
| 리랭커 입력 길이 상한 1,024토큰 | 최악의 경우를 묶음 | 현재 데이터(최대 817토큰)에서는 없음 | 적용 |
| fp16 | 가중치·계산 모두 절반 | 조금 바뀜, 평가 기준선 재측정 필요 | 보류 |
| 개발·평가 공용 모델 서버 | 두 환경 동시 실행 시 중복 제거 | 없음 | 보류 (둘을 동시에 띄울 때만 필요) |

### 적용 내용 (커밋 `dc6e81e1`)

- `embedding-server/app/reranker.py`
  - `RERANK_BATCH_SIZE` 기본값 32 → 8
  - `RERANK_MAX_LENGTH` 신설, 기본값 1,024
  - `CrossEncoder(..., max_length=RERANK_MAX_LENGTH)`
- 평가 설정 `compose.common-evaluation.yaml`과 개발 설정 `docker-compose.stack.yml`에 두 값을 명시했다.
- `/health` 응답에 `reranker_max_length`를 추가했다. 실행 기록마다 실제 적용값이 남는다.
- 평가 검색 컨테이너만, 원래 쓰던 compose 파일 세 개로 다시 만들었다. 만들기 전에 실행 중인 컨테이너와 새 설정의 환경 변수를 비교했다(비밀값은 해시로 비교). 바뀐 값은 위 두 개뿐이었다.

## 5. 한계와 남은 일

- **1,024토큰 상한**: 앞으로 이보다 긴 장소 설명이 들어오면 뒷부분이 잘린 채 리랭크된다. 데이터가 바뀌면 길이 분포를 다시 확인해야 한다.
- **fp16은 적용하지 않았다.** 메모리를 더 줄일 수 있지만 검색 점수가 바뀌어 평가 기준선을 다시 재야 한다.
- **개발·평가 동시 실행**: 두 검색 컨테이너가 각각 모델을 올리므로 6GB GPU에 동시에 들어가지 않는다. 지금은 한 번에 하나만 띄운다. 둘 다 필요해지면 공용 모델 서버 방식을 쓴다.
- **이전 측정값**: 이전 사례 글의 사전 검색 시간(최대 32.7초)도 같은 원인이었을 수 있다. 확인하지는 않았다.

## 6. 배운 점

- **기다림인지 계산인지부터 나눈다.** 같은 입력이 매번 같은 시간 걸리면 대기열이 아니라 계산 문제다. 처음에 Kafka 재합류를 의심했지만, 구간을 나눠 재자 바로 배제됐다.
- **Windows에서는 `nvidia-smi`만으로 부족하다.** WDDM에서는 프로세스별 사용량이 `N/A`로 나오고, 시스템 RAM으로 밀려난 양도 보이지 않는다. `\GPU Process Memory(*)\Shared Usage` 카운터가 결정적이었다.
- **GPU 메모리가 넘쳐도 오류가 나지 않는다.** Windows는 넘친 부분을 시스템 RAM으로 옮겨 계속 실행한다. 실패 대신 10배 느려지기만 해서 원인을 찾기 어렵다.
- **배치 추론의 메모리는 묶음 크기 × 길이²로 커진다.** 모델 기본 최대 길이를 그대로 두지 말고 실제 입력 분포를 재서 상한을 정한다.
