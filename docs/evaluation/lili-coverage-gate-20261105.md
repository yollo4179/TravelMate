# 장소 데이터 범위로 범위 밖 요청 막기 (2026-11-05)

## 목적

LiLi가 데이터에 없는 지역을 안내하는 틀린 안내를 없앤다. MVP의 세 출구 중 "범위 밖이면 정해진 안내"를 실제로 작동하게 한다.

- 근거(`1d6ad65d`의 g1과 반복·보류 실행, [lili-result-consistency-20261105.md](lili-result-consistency-20261105.md)):
  - 범위 밖 지역(해운대·제주·강릉)을 물으면 12번 모두 "부산(제주, 강릉)으로 범위를 바꿔서 다시 찾아"라고 안내했다. 데이터에는 서울뿐이라 바꿔도 결과가 없다.
  - 라우터 지역 충돌 규칙 때문에 해수욕장 문항이 6번 중 3번 검색을 건너뛰었다.
- LLM은 지역을 안다(12번 모두 해운대를 부산으로 알았다). 모르는 것은 우리 데이터에 무엇이 있는지다. 그래서 지역 이름 고르기는 LLM이, 데이터에 있는지 확인은 코드가 한다.

## 바꾼 것

| 단계 | 변경 |
|---|---|
| 데이터 범위 | 서버가 `places`의 실제 지역·분류를 읽는다(`PlaceCoverageService`, 10분마다 다시 읽음). 지금은 서울·관광지다. 읽지 못하거나 모르는 지역 이름이 있으면 판정을 끄고 예전처럼 검색한다 |
| 라우터 입력 | 데이터 범위(`searchCoverage`)를 사실로 넣는다 |
| 라우터 출력 | 사용자가 말한 곳의 시·도(`requested_region`)를 17개 목록에서 고른다. 정할 수 없으면 비운다 |
| 범위 밖 판정 | 장소 검색·되묻기 갈래에서 고른 시·도가 데이터에 없으면, 코드가 검색 없이 정해진 LiLi 문구로 끝낸다(`PlaceCoverageGate`). 문구: "부산 쪽 장소는 아직 내 자료에 없어. 지금은 서울 관광지만 찾을 수 있어." 판정은 `COVERAGE` 사건으로 남는다 |
| 라우터 규칙 | 검색 전에 지역 충돌로 되묻던 규칙을 지웠다. 대신 "맞는 장소가 있는지는 검색 결과로만 안다"를 넣었다 |
| 추천 설명 | 같은 범위를 받는다. "앱에서 범위를 바꿔 요청하라"는 "데이터에 있는 지역·분류만 제안한다"로 바꿨다 |
| 평가 | `V3-D-outside-catalog`와 보류 문항 `V3H-outside-jeju`, `V3H-outside-gangneung-no-filter`의 기대를 "검색 없이 범위 밖 안내"(`OUT_OF_COVERAGE`)로 바꿨다(사용자 결정). 채점: 시·도를 맞게 골랐는지, 서버가 막았는지, 검색이 없었는지 |

문항 해시: v3 `1f0309f2d392…`, 보류 `e81e1a43038b…`(입력은 그대로, 기대만 바뀜).

## 실측 (`20261105-lili-v3-k1`과 `-restN`, `20261105-lili-v3h-k1`)

호출 76회, 캐시 할인 전 $0.169. 라우터 입력 중앙값은 1,884 → 2,213토큰으로, 범위 정보와 새 칸 설명만큼 늘었다.

### 고치려던 것

| 문항 | 결과 |
|---|---|
| 해운대·제주·강릉 | 3/3. 시·도를 부산·제주·강원으로 맞게 골랐고, 검색 없이 정해진 안내로 끝났다 |
| 해수욕장 | 검색했다. "서울 안에서 분위기나 산책 느낌으로 다시 좁혀줄까?"처럼 데이터 안의 제안만 했다(g1까지는 6번 중 5번 "바다 쪽 지역으로" 제안) |
| 스키(보류) | 검색했다. "지금 범위에선 관광지만 볼 수 있어서"라고 데이터 범위를 말했다 |
| 호텔 예약 | 호텔을 찾아 주겠다는 제안이 사라졌다(c1·g1에서는 있었다) |
| 운영시간·주차 | 없는 자료를 찾아 주겠다는 제안이 없었다 |

## 한계

- 한 번씩만 돌렸다. 범위 밖 3문항은 모두 맞았지만 반복 횟수가 적다.
- 의미 판정은 Claude 초안이다.
- 개발용 서버는 다시 띄울 때 새 코드가 이 판정을 쓴다. 이번에는 DB 변경이 없다.
