# JSON은 맞았는데 검색 결과는 없었다: OpenAI strict 검색 도구 연결을 확인한 과정

> 블로그 초안. 이 글의 완료 범위는 기존 두 문항의 검색 도구 연결 검증이다. 전체 호출 신뢰성이나 모델 성능 벤치마크를 완료한 기록은 아니다.

여행 앱에서 장소를 검색하는 도구를 모델에 연결했다. 모델은 `search_places`를 선택하고 검색어와 지역·분류 필터를 넘긴다. 서버는 검색 결과와 근거를 모델에 전달하고, 모델은 이를 이용해 설명을 만든다.

실제로 확인하고 싶었던 것은 단순했다. 창경궁을 찾아달라는 요청과 종로의 조선 왕실 가족 거처를 찾아달라는 요청이 이 경로를 끝까지 통과하는지 보는 것이었다. 두 번째 요청에서는 도구 실행 자체가 성공했는데도 결과가 비었다. 응답 JSON의 문법보다 검색 필터를 살펴봐야 했다.

## 첫 번째 발견: 모델이 선택한 분류와 DB의 분류가 달랐다

모델은 두 번째 요청에서 다음 인자를 만들었다. 읽기 편하도록 필드 순서와 공백을 정리한 발췌이며, 실제 원본 문자열은 연결한 평가 기록에 남아 있다.

```json
{
  "query": "조선 왕실 가족이 생활했던 궁 또는 거처",
  "region": "서울",
  "city": "종로",
  "category": "궁",
  "limit": 10
}
```

이 실행에서 `category`는 문자열을 받을 수 있었으므로 형식 검증을 통과했다. 하지만 검색 필터의 `category`는 DB의 대분류 값과 정확히 맞아야 했다. 동결 자료에서 창경궁·운현궁·낙선재·건청궁의 분류는 `관광지`였다. 실제 검색 추적에는 `category="궁"`, 후보 0개가 기록됐다.

`궁`이라는 단어가 틀린 것은 아니다. 사용자가 찾는 장소의 세부 유형으로는 의미가 있지만, 이 DB의 분류 필터에 넣을 값은 아니었다. 이 사례에서는 도구 호출의 형식과 필터 선택의 적절성을 따로 확인해야 했다.

## 저장과 검색이 같은 분류 정의를 사용하게 했다

현재 저장 코드는 `TourContentType.getLabel()`을 `places.category`에 넣는다. 검색 계약도 이 enum의 분류명을 사용하도록 맞췄다. 별도의 단어별 변환표를 두지 않고, 같은 정의에서 도구 스키마의 enum과 서버 허용값을 가져왔다.

저장 경로가 지원하는 분류는 관광지·문화시설·축제공연행사·여행코스·레포츠·숙박·쇼핑·음식점의 8개다. 다만 보존된 평가 스냅샷 449행에서는 `관광지`만 관측됐다. 지원 분류 8개를 모두 실제 모델로 평가했다는 의미는 아니다.

계약은 다음과 같이 정리했다.

- `category`에는 허용된 대분류 또는 null을 사용한다. 생략·null의 기존 검색 조건 상속 규칙도 유지한다.
- 궁·왕실 가족의 거처 같은 세부 유형과 관계는 `query`에 남긴다.
- 도구가 넘긴 값과 상속된 조건을 서버에서도 검증한다.
- 허용되지 않는 값을 자동으로 고치거나 필터를 지워 성공시키지 않는다.

실제 `category="궁"` 인자를 회귀 자료로 남겼다. 서버가 이를 거부하고 검색을 호출하지 않는지, 원래 인자를 보존하는지, 허용된 분류와 query는 바꾸지 않고 전달하는지를 오프라인으로 확인했다.

## 두 번째 발견: 평가 코드도 평가를 막을 수 있었다

모델 호출과 별개로 평가를 준비하는 과정에서도 두 번 막혔다. 두 경우 모두 OpenAI에 전달된 요청은 0회였으므로 모델 품질 실패로 집계하지 않았다.

첫 번째는 기록용 중계기의 HTTP 본문 읽기였다. 중계기는 `Content-Length`만 보고 본문을 읽었지만 실제 Java 클라이언트는 chunked 방식으로 전송했다. 빈 본문을 JSON으로 해석하다 실패했다. 실제 클라이언트가 생성하는 요청으로 오프라인 전송을 확인하고 본문 처리만 수정했다.

다음에는 배포한 도구 스키마와 기대 스키마가 같은지 확인하는 비교가 문제였다. `required`에 들어 있는 필드 집합은 같았는데 배열의 나열 순서가 달랐다. 단순 JSON 비교는 이를 불일치로 판단했다.

수정 범위는 비교 함수로 한정했다. 비교용 복사본에서 `required`의 순서만 무시하고, 실제 요청 본문은 정렬하거나 다시 직렬화하지 않았다. 필수 필드 추가·누락·중복, category enum, 타입, 추가 필드 허용 정책이 달라진 경우에는 계속 차단했다. 원래 요청의 배열 순서와 바이트 해시도 유지했다.

이 과정을 기록할 때는 실패의 위치를 분리했다. 로컬 전송·비교 실패와 실제 모델의 잘못된 인자 선택을 같은 실패율로 합치면 무엇을 고쳐야 하는지 알기 어렵다.

## 기존 두 문항에서 확인한 결과

최종 실행은 `gpt-5.4-mini-2026-03-17`로 기존 두 문항을 각각 한 번 수행했다. 추론 4회, 토큰 계산 4회, 검색 2회를 사용했다. 재시도·계획·judge·추가 문항 호출은 없었다.

| 요청 | 실제 category | 결과 |
|---|---|---|
| 창경궁을 찾아줘 | 관광지 | 5개 반환, 창경궁이 1위 |
| 종로의 조선 왕실 가족 거처 | 관광지 | 5개 반환, 동결 정답의 관련 장소 4개 포함 |

두 번째 결과에는 서울 운현궁·창경궁·건청궁·창덕궁 낙선재가 포함됐다. 서버의 적용 필터도 모델이 선택한 `관광지`와 같았다. 서버가 `궁`을 `관광지`로 바꾼 결과가 아니다. 이전의 잘못된 category 때문에 검색이 비던 문제는 이번 두 문항 실행에서 재현되지 않았다.

최종 배치의 단계별 시간은 다음과 같다. 계산·추론은 문항별 두 번의 합계이며, 전체는 클라이언트에서 측정한 개별 요청 시간이다.

| 문항 | 토큰 계산 | 추론 | 검색 도구 | 전체 |
|---|---:|---:|---:|---:|
| 창경궁 조회 | 3.006초 | 5.686초 | 3.735초 | 12.927초 |
| 왕실 가족 거처 조회 | 1.542초 | 4.653초 | 2.306초 | 8.539초 |

두 개의 개별 시간일 뿐이다. 이를 평균 성능이나 p95로 제시하지 않았고, 이전 실행과의 차이를 category 수정의 속도 개선 효과로 해석하지 않았다. 검색어·반환 한도·캐시와 모델 준비 상태가 동일한 통제 실험이 아니기 때문이다.

공급자가 반환한 입력 토큰은 11,428개, 그중 캐시 입력은 2,816개, 출력은 577개였다. 실행 당시 승인 단가를 적용한 추론비는 캐시 할인 반영 기준 `$0.00926670`이었다. 토큰 계산 API의 별도 비용과 총 청구액은 미확인이라 null로 남겼다. 이 숫자를 청구서 확정 금액이나 총 `$0.10` 보장으로 표현하지 않았다.

## 검색이 성공해도 남는 문제

첫 번째 최종 query에는 사용자가 요청하지 않은 `조용한`, `산책 가능한` 특성이 추가됐다. 검색 결과에 창경궁이 잘 나왔다는 이유로 이 확장을 적절하다고 판정하지 않았다. 도구 설명의 예시가 영향을 줬을 가능성은 생각할 수 있지만, 이번 기록만으로 원인을 확정하지 않는다.

두 번째 설명은 창경궁·낙선재·운현궁을 언급했지만 정식 인용은 창경궁 1건뿐이었다. 그 인용은 실제 전달된 원문과 장소·근거·출처 ID가 일치했다. 그러나 낙선재와 운현궁의 설명까지 충분히 인용됐다고 볼 수는 없다.

검색어의 불필요한 확장과 일부 장소의 정식 인용 부족은 미해결 개선 후보로 남겼다. 이를 고치기 위한 추가 기능 개발이나 재시험은 하지 않았다.

## 이 글에서 말할 수 있는 범위

기존 두 문항에서 strict 스키마 전달, 도구 선택, 인자 전달, 검색, 결과 기반 설명까지 연결되는 것을 확인했다. 선택된 category의 허용값 준수와 그 필터의 적절성도 이 범위에서 확인했다.

전체 호출 신뢰성, 반복 안정성, 평균 성능·p95, 8개 분류 전체, 일정 생성·수정은 아직 이 기록으로 판단할 수 없다. 이번 사례에서 얻은 것은 작은 연결 검증을 실제 인자와 단계별 기록으로 확인한 경험이다.
