## 같은 질의로 두 검색 모드를 비교했다
{: #comparison }

리랭킹이 검색 결과를 얼마나 바꾸는지 보려고 의미 검색만 사용한 결과와 리랭킹을 거친 결과를 비교했다. 2026년 10월 26일, 같은 장소 검색 질의 80개를 두 모드의 Spring 검색 API에 각각 보냈다. 두 모드 모두 pgvector에서 후보를 최대 30개 찾지만, API 호출마다 후보 검색을 새로 실행한다. 따라서 두 응답이 완전히 같은 후보 목록에서 출발했다고 가정하지 않았다.

<pre><code class="language-mermaid">
flowchart LR
    Q([검색 질의 80개]) --> S[의미 검색 API]
    Q --> R[[리랭킹 API]]
    S --> T[(모드별 응답 시간 80건)]
    R --> T
    S --> C{요청 조건 적용 여부}
    R --> C
    C -->|완전 적용 60문항| M([검색 순위 품질 계산])
    C -->|일부 미적용 20문항| X([품질 평균에서 제외])
</code></pre>

두 모드 모두 80개 요청에 응답했다. 다만 20개 질의는 요청 조건을 서버가 완전히 적용하지 못해 품질 평균에서 뺐다. 아래 품질 지표는 나머지 60개 질의만 계산한 값이다. 장소의 적합도 판정도 일부 후보에만 있으므로, 판정되지 않은 장소를 오답이라고 보지는 않았다.

## 상위 결과는 좋아졌고 응답은 느려졌다
{: #search-quality }

### 검색 품질 평가 결과 · 조건 적용 60문항

| 지표 · 60문항 평균 | 의미 검색 | 리랭킹 | 차이 |
| --- | ---: | ---: | ---: |
| Top-1 정확도 | 83.3% | 88.3% | +5.0%p |
| Hit@5 | 96.7% | 100% | +3.3%p |
| Recall@5 | 87.1% | 92.8% | +5.8%p |
| NDCG@10 | 0.850 | 0.907 | +0.056 |

Top-1은 첫 번째 장소가 알려진 적합 장소인지, Hit@5는 상위 다섯 곳에 적합 장소가 하나라도 있는지를 본다. Recall@5는 알려진 적합 장소 중 다섯 곳 안에 들어온 비율이고, NDCG@10은 적합한 장소가 앞에 놓였는지를 점수로 계산한다. <span class="notice-yellow">리랭킹 모드의 첫 결과 정확도는 83.3%에서 88.3%로 높았다.</span>

### 전체 응답 시간 · 모드별 80건

| 전체 HTTP 응답 · 모드별 80건 | 의미 검색 | 리랭킹 | 차이 |
| --- | ---: | ---: | ---: |
| 평균 | 1.011초 | 1.607초 | +0.596초 |
| p95 | 1.514초 | 2.015초 | +0.501초 |

사용자가 기다리는 전체 응답은 평균 0.596초 길어졌다. 이 시간에는 Spring과 Kafka를 거치는 과정, 질의 임베딩, DB 검색, 리랭킹이 함께 들어 있다. 리랭커 모델만의 처리 시간과는 구분해야 한다.

## 리랭커 자체의 처리 시간을 줄였다
{: #reranker-latency }

전체 응답에서 리랭커가 쓰는 시간을 줄이기 위해 질문과 후보 장소 30개의 ID·본문을 고정했다. 조건을 완전히 적용할 수 있었던 60문항에 대해 BGE 리랭커의 FP32 실행과 CUDA FP16 자동 혼합 정밀도를 배치 크기 8·16·32로 비교했다. GPU는 RTX 4050 Laptop GPU였다. 아래 시간은 리랭커 호출만 측정한 값으로, HTTP·Kafka·임베딩·DB 검색 시간은 빠져 있다.

### 고정 후보 리랭커 처리 시간 · 60문항

| 실행 방식 | 배치 크기 | 평균 | p95 |
| --- | ---: | ---: | ---: |
| FP32 | 8 | 1.527초 | 2.187초 |
| FP32 | 16 | 2.760초 | 12.395초 |
| FP32 | 32 | 13.728초 | 24.258초 |
| FP16 자동 혼합 정밀도 | 8 | 0.547초 | 0.717초 |
| FP16 자동 혼합 정밀도 | 16 | 0.656초 | 0.865초 |
| FP16 자동 혼합 정밀도 | 32 | 1.530초 | 3.559초 |

같은 배치 크기 8에서 FP16 방식은 FP32의 평균 1.527초를 0.547초로 줄였다. 약 2.8배 빠른 값이다. 모델의 가중치를 FP16으로 바꾼 것은 아니고, GPU가 지원하는 연산에 FP16 자동 혼합 정밀도를 적용했다.

여섯 설정 모두 사람의 적합도 판정으로 계산한 60문항의 순위 지표 15개가 기준 설정보다 낮아지지 않았다. 선택한 FP16·배치 8은 60문항 중 41문항에서 후보 30개의 전체 순서까지 FP32·배치 32와 같았다. 나머지 19문항은 일부 순서가 달랐으므로, <span class="notice-yellow">판정되지 않은 장소까지 품질이 같다고 말할 수는 없다.</span> 이 범위에서 FP16·배치 8을 선택했고, 앞의 전체 HTTP 응답 시간도 이 설정을 적용한 뒤 측정했다.
