# 이동 근거 직접 벡터 검색 비교

문서 버전: 1 · 실행·작성: 2026-11-01 · 기준: `acc5a267` · 브랜치: `feat/contextual-relation-vector-retrieval`

**고정한 합성 스트레스 사례에서 기존 Top-30에 없던 보조 이동 근거가 후보 1위에 도달했고, 원문 리랭킹도 해당 근거를 대표로 선택했다.**
같은 활성 청크와 검수 자료에서 이동 인용 벡터만 추가한 결과다. 활성 20개 밖에 있던 역방향 관계는 여전히 검색되지 않았다.
일반 검색 품질·전체 지연·운영 효과까지 입증한 결과는 아니다. 기본 검색은 `chunk-only`를 유지한다.

## 구현 범위

- `CONTEXTUAL_RELATION_RETRIEVAL=chunk-only`가 기본값이다. `chunk-and-relation-v1`을 명시한 경우, 색인 작업자가 **선택된 활성 청크**의 검증된 독립 관계마다 정확한 evidence.quote를 BGE-M3로 별도 임베딩한다. 예상 질문을 생성하지 않는다.
- `retrieval_relation_embeddings`에 chunk_id/context_version/relation_index/표현 버전·원문 evidence·1024차원 벡터를 저장한다. 원래 청크 전체 문맥+원문 벡터도 유지한다. SQL trigger는 해당 관계 순번·정확한 원문 위치·인용·type/importance의 일치를 검사한다.
- 추가 벡터 저장은 기존 색인 세대 CAS가 성공한 트랜잭션 안에서만 수행한다. 원본·스냅샷·청크 세대가 바뀌면 기존 활성 링크와 새 관계 벡터를 쓰지 않는다.
- 명시적 이동 관찰 필터가 있는 검색에서만 두 표현을 함께 조회한다. 출발지·도착지·결과 endpoint·primary/supporting 조건은 **벡터를 선택하기 전에 개별 관계에도** 적용한다. 한 관계의 높은 점수로 다른 관계의 방향 조건을 우회하지 않는다.
- 각 활성 청크에서 전체 벡터와 일치하는 관계 벡터 중 최고 cosine 하나, 각 장소에서도 최고 근거 하나를 고른다. 경로 수·청크 수에 따른 점수 합산은 없다. 같은 장소는 한 후보이며 최종 Top-30·리랭킹 근거 수 한도는 유지한다.
- 후보와 추가 근거 조회에 같은 표현 선택을 적용한다. 관계 벡터로 찾았으면 그 관계의 원문 인용과 출발지·도착지만 리랭커에 넘긴다. 보존된 전체 청크와 장소의 subject/mentioned는 바꾸지 않는다.
- 기존 v6처럼 관계 인용이 명시되지 않은 자료에 인용을 만들어 넣지 않는다. 별도 벡터가 없는 청크는 기존 전체 벡터 경로를 사용한다. 경관·시설·관찰 필터 없는 검색은 그대로다.
- Docker Compose와 bootstrap에도 설정 전달·유효성 검사·제거 시 기본값 복귀를 연결했다. 실제 운영 설정·컨테이너는 갱신하지 않았다.

## 비교 조건과 검수

기존 Sonar 응답을 재생성하지 않았다. [서버 위치 재처리](../../v8-server-evidence-v1/20261101-01/REPORT.md)에서 복구한 합성 CONTROL 4개를 원문·주체·방향·supporting 기준으로 에이전트가 검수했다.
실제 P09는 기존 검수 승인 8개만 사용했다. 복구된 P09의 추가 형식 후보를 자동으로 승인하지 않았다. 버전을 아는 개발 검수이며 블라인드 인간 평가가 아니다.

CONTROL의 혼합 원문:

```text
A공원은 야경이 아름답고, 관람 후 B공원으로 걸어갈 수 있다.
```

경관의 subject는 A(101), B(202)는 mentioned를 유지했다. 별도로 임베딩한 보조 이동 근거는 `관람 후 B공원으로 걸어갈 수 있다.`다.
`A→B`, supporting, evidence `[15:35]`를 확인했다. ‘가깝다·편하다·쉽다’는 내용을 덧붙이지 않았다.

| 항목 | 두 비교군에 공통 |
|---|---|
| 고정 질문 | 기존 6개 |
| 유효성·검수 | 같은 처리·승인 청크 12개 |
| 방해 사례 | 기존 차량 전용·도보 금지 합성 40개 |
| 활성 청크 | 장소별 최대 20개, 동일한 선택 결과 |
| 장소 후보 | 최대 30개 |
| 리랭킹 근거 | 장소별 최대 2개 |
| 모델 | 기존 BGE-M3 / BGE-reranker-v2-m3 |
| 변경 변수 | 청크 전체 벡터만 / 전체 벡터+이동 인용 벡터 |

B의 유효 청크는 44개, 활성은 20개다. 보조 관계는 기존과 동일하게 선택 순서 44번째이며, 슬롯을 예약하거나 상한을 늘리지 않았다.
전체/관계 벡터를 같은 격리 DB에 저장하고 검색 모드만 바꿔 12조건을 실행했다. 기준군은 관계 벡터 테이블을 검색하지 않는다.

## 계산 재사용과 비용·지연

- 기존 임베딩 **58개**를 재사용했다. 새로 임베딩한 고유 문장은 **4개**, `/embed`는 **1회**다. 선택된 관계별 저장 행은 **43개**이며 같은 부정 인용을 반복 임베딩하지 않았다.
- 이전 결과에서 동일한 질의·리랭킹 텍스트 점수 캐시 **65쌍을 준비**했다. 65는 가용 캐시 항목 수이며 실제 사용 횟수가 아니다. 누락된 텍스트만 `/rerank` **3회·9개 입력**으로 추가 계산했고, 이후 같은 입력은 다시 호출하지 않았다.
- Perplexity·Sonar 유료 호출 **0회**, 운영 DB 쓰기 **0회**다. 임시 격리 DB에만 자료·벡터를 썼다. 기존 모델 서비스 이미지는 이전 실행과 동일함을 확인했다.
- SQL 후보·근거 조회 시간은 단회 값만 기록했다. 실행 순서·DB 캐시·이전 모델 점수 재사용이 있으므로 전체 지연 비교·속도 개선으로 해석하지 않는다.
- 공개 결과는 원문 전체를 제외했다. 원본 비교 결과·실제 벡터·추가 모델 입력/점수·검수 승인·실행 당시 코드는 로컬에 보존했다.
- 원본 결과의 `reused_query_text_scores=65`는 가용 캐시 수다. 공개 결과와 후속 실행 코드는 `available_saved_query_text_scores`로 이름을 명확히 했다. 원본 파일은 수정하지 않았다.

## 검증과 운영 적용 조건

- 새 서버 검사 **19개**(단위 8·점수 재사용 4·실제 PostgreSQL 7), 새 bootstrap 검사 **1개**를 추가했다.
- 실제 PostgreSQL 17.10/pgvector 0.8.5를 사용한 서버 전체 **144개 중 143개 통과·기존 모델 플래그 1개 skip**이다. Docker bootstrap·shell은 **13개 통과**다.
- 다른 관계의 고득점이 방향 조건을 우회하지 않음, 관계 순번·인용·위치 불일치 SQL 거부, 후보 중복 제거, 원문 리랭킹, 비활성 endpoint 검색 제외, CAS 실패 시 새 벡터 미저장을 확인했다.
- 마지막 테스트 스키마 수는 0개였다. 임시 DB·runner·내부 네트워크를 삭제했고 운영 서비스를 재시작하지 않았다.

[테스트 집계](tests.json) · [실행 환경](environment.json) · [정리 확인](cleanup.json)

아직 운영 적용하지 않았다. 향후 명시적으로 선택할 때만 source.env에 `CONTEXTUAL_RELATION_RETRIEVAL=chunk-and-relation-v1`을 설정한다.
관계 벡터는 다음 색인 작업에서 생성되므로 설정 변경만으로 기존 청크에 벡터가 생기지 않는다. 검수된 대상에 대한 재색인 작업과 스키마 적용이 필요하다.
동일한 번들 재적용은 ALREADY_APPLIED이므로 재색인 등록과 구분해야 한다. 기존 명세의 표본 재색인 절차를 사용하되 이번에는 운영에 실행하지 않았다.
설정을 제거하면 chunk-only 검색으로 돌아가며 저장된 벡터가 활성 범위를 늘리지 않는다. Spring/UI의 자연어 이동 의도→구조화 observation 필터 연결은 이번 범위가 아니다.

## 남은 결정과 한계

- 활성 20개를 ‘검색 가능한 청크 수’로 유지할지, 검수 청크를 모두 검색하고 질문별 근거만 제한할지는 결정하지 않았다. 이번에는 기존 의미를 유지했다.
- 예상 질문 벡터를 추가하지 않았다. 표현 차이로 놓치는 사례가 남는지 확인한 뒤 보조 경로로 검토해야 한다. 원문에 없는 편의성 판단이나 인용 근거로 사용할 수 없다.
- 잘못된 장소·관계·주체 판정은 별도 의미 검수 대상이다. 직접 인용 벡터도 잘못된 귀속을 교정하지 않는다.
- 합성 방해 40개가 포함된 작은 감독 검증이다. 전체 장소·질문 분포·실제 운영 데이터·대규모 SQL 비용·동시성 성능을 대표하지 않는다.
- 길이가 다른 전체/인용 벡터의 최고 cosine을 사용하는 선택 정책도 일반 분포에서 별도 검증이 필요하다. 이번 한 사례의 성공으로 기본값을 바꾸지 않았다.
