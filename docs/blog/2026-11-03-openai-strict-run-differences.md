01·03의 숫자 0은 제공자로 전달된 호출이 없었다는 뜻이다. 앱의 로컬 문항 요청·토큰 계산 시도는 각각 있었으며 실패 기록에 남아 있다. 두 실행은 모델 품질 실패에서 제외한다. 02·04는 같은 기존 두 문항을 서로 다른 단계에서 실행한 기록이며, 모든 단계의 호출을 최종 배치 한 번의 호출 수로 합치지 않는다.

모든 단계의 모델 지정과 비용 가드 클래스는 같았다. 앱 변경은 02→03의 category 계약·서버 검증 반영이고, 03→04에는 앱 JAR 변경이 없다. 마지막 차이는 중계기의 비교 처리뿐이다.

## 블로그로 쓰기 좋은 소재

| 소재 | 보여줄 실제 사례 | 주장할 수 있는 내용 | 확대하면 안 되는 내용 |
|---|---|---|---|
| 출력 형식과 검색 의미의 차이 | 유효한 JSON의 category=궁, 검색 후보 0개 | 이 사례에서는 분류 선택이 검색 실패의 핵심이었다 | strict 전체의 무용성이나 모든 실패 원인 |
| 저장·스키마·서버 검증의 연결 | 저장 enum을 공유하고 미허용 분류를 거부 | 두 문항에서 관광지 선택과 실제 필터 적용 확인 | 8개 분류 전체의 실제 모델 검증 |
| 평가 환경 실패 분리 | 본문 읽기 오류, required 순서 비교 오류 | 제공자 호출 전 중단을 모델 품질 실패에서 제외 | 실제 호출 성공률·전체 신뢰성 |
| 원본을 바꾸지 않는 비교 | required 비교 복사본과 원래 전송 해시 | 실제 요청의 순서·바이트를 보존하면서 비교만 수정 | 모든 JSON 배열을 순서 없이 비교해도 된다는 주장 |
| 예산과 미확인 비용의 기록 | 호출 상한, 추론 사용량, 계산 비용 null | 확인 가능한 추론비와 미확인 비용을 구분 | 계산 API 무료, 총 청구액 0.10달러 보장 |
| 검색 성공 후 남는 문제 | 불필요한 query 확장, 정식 인용 부족 | 연결 성공과 설명 품질을 나눠 기록 | 두 개선 후보가 해결됐다는 주장 |

추천 글의 중심은 **category 선택 오류를 실제 인자·적용 필터·검색 결과로 추적한 과정**이다. 중계기 실패 두 건은 평가 기록을 해석하는 과정의 별도 소주제로 연결할 수 있다.

## 미해결·미검증 경계

- 요청에 없던 `조용한·산책 가능한` 검색어 추가: 미해결 개선 후보다. 예시 문구의 영향은 원인 가설이며 확정하지 않았다.
- 두 번째 설명의 낙선재·운현궁 정식 인용 부족: 미해결 개선 후보다. 창경궁 인용의 일치를 답변 전체의 근거 충족으로 확대하지 않는다.
- 전체 호출 신뢰성·반복 안정성·평균 성능·p95·8개 분류 전체·일정 생성·수정은 미검증이다.
- 이전 배치와 최종 배치는 query·반환 한도·캐시·검색 모델 준비 상태가 같지 않다. 지연 차이를 수정 효과의 통제 실험으로 쓰지 않는다.

## 로컬 실행 폴더와 정리 범위

네 로컬 실행 폴더는 블로그를 작성하기 위해 통째로 유지할 필요는 없다. Git에 보존된 기록은 해당 커밋과 경로로 확인할 수 있다. JAR와 오프라인 추출 라이브러리·클래스, Python 캐시는 기록을 읽는 데 필요하지 않은 빌드·실행 산출물이다.

폴더를 정리할 때 Git에 없는 소스·로컬 설정·미수록 원본은 별도로 남긴다. 키가 들어 있는 설정은 블로그나 Git에 올리지 않는다. 실제 요청·응답 원본과 후속 개선 항목을 보고서의 요약 문장만으로 대체하지 않는다. C02·C03·미포함 C05 및 다른 작업 트리·공유 모델 캐시는 이 정리 범위 밖이다.
