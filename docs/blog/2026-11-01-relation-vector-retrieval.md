# 원문에 있는 이동 근거를 검색이 놓칠 때: 이동 인용 벡터를 추가한 기록

여행 장소를 검색할 때는 한 장소의 특징뿐 아니라 장소 사이의 연결도 중요하다. 사용자가 “B공원으로 걸어서 갈 수 있는 곳”을 물었다면, 검색기는 B공원에 도보로 연결되는 출발 장소를 찾아야 한다.

TravelMate의 고정 검색 실험에서는 이 질문에 답할 수 있는 원문이 저장돼 있었는데도 해당 장소가 검색 후보에서 빠졌다. 이전 진단에서 올바른 이동 근거의 벡터 순위는 41위였고, 리랭커에 전달하는 후보 상한은 30개였다. 리랭커가 근거를 읽기도 전에 후보 검색에서 탈락한 것이다.

이번에는 검증된 이동 인용을 별도로 임베딩해 검색 경로에 추가했다. 같은 활성 청크와 모델, 후보 상한을 유지한 비교에서 대상 장소는 **후보 1위와 리랭킹 최종 1위**에 도달했다.

이 글은 2026년 11월 1일 커밋 `1e646b33`의 구현과 고정 비교를 정리한 기록이다. 개선을 확인한 핵심 사례는 A공원과 B공원을 사용한 합성 자료이며, 전체 검색 품질이나 운영 효과를 검증한 결과는 아니다.

**문장 하나에 경관 설명과 이동 설명이 함께 있었다.**

실험에 사용한 원문은 다음과 같다.

> A공원은 야경이 아름답고, 관람 후 B공원으로 걸어갈 수 있다.

이 문장에는 두 가지 정보가 담겨 있다. 앞부분은 A공원의 경관을 설명한다. 뒷부분은 방문자가 A공원을 관람한 뒤 B공원으로 걸어갈 수 있다는 이동 정보를 설명한다. 원문에 방문자의 이름이나 실제 이동 경험이 적혀 있는 것은 아니므로, 특정 사람이 실제로 걸었다고 해석해서는 안 된다.

| 구분 | 주체 또는 대상 | 원문에서 확인하는 내용 |
|---|---|---|
| 경관 | A공원 | 야경이 아름답다 |
| 이동하는 사람 | 문맥상 A공원을 관람한 방문자 | 관람 후 B공원으로 걸어갈 수 있다 |
| 출발지 | A공원 | 관람을 마치고 출발하는 장소 |
| 도착지 | B공원 | 걸어서 이동할 수 있는 목적지 |

이동 방향은 **A공원 → B공원**이다. 이 문장으로 B공원의 야경이 아름답다거나 B공원에서 A공원으로도 걸어갈 수 있다고 판단할 수는 없다.

저장된 경관 설명에서도 A공원은 `subject`, B공원은 `mentioned`로 유지했다. A→B 이동 관계는 별도로 표현했다. 경관 설명에 덧붙은 이동 정보이므로 관계의 비중은 `supporting`으로 분류했다. 여기서 supporting은 보조 내용이라는 뜻이며, 근거의 신뢰도가 낮다는 의미는 아니다.

**“B로 갈 수 있는 곳”에서 찾아야 하는 대상은 출발지다.**

실험 질문은 “B공원으로 걸어서 갈 수 있는 곳”이었다. B공원은 질문에서 이미 지정한 도착지다. 검색 결과로 찾아야 하는 대상은 B공원까지 걸어갈 수 있는 출발 장소이며, 위 원문이 뒷받침하는 장소는 A공원이다.

이 실험에서는 검색기에 도착지 B공원과 보조 관계라는 구조화 조건을 명시적으로 전달했다. 해당 조건에서 반환할 장소는 관계의 출발지다. 사용자의 자연어를 읽어 구조화된 이동 조건을 자동으로 만드는 Spring/UI 연결은 이번 구현에 포함하지 않았다.

| 질문 | 이미 지정된 장소 | 검색 결과로 찾는 대상 | 원문이 뒷받침하는 장소 |
|---|---|---|---|
| B공원으로 걸어서 갈 수 있는 곳 | 도착지 B공원 | 출발지 | A공원 |
| A공원에서 관람 후 걸어서 갈 수 있는 공원 | 출발지 A공원 | 도착지 | B공원 |

두 질문 모두 같은 A→B 관계를 이용하지만 검색 결과로 요구하는 장소는 다르다. 이 구분은 뒤에서 설명할 활성 청크 제한에도 영향을 준다.

**기존 검색에서는 올바른 근거가 Top-30 밖으로 밀렸다.**

기존 방식은 청크 전체의 문맥과 원문을 임베딩한 벡터로 후보를 검색했다. 청크는 검색을 위해 저장한 원문 단위다. 예시 청크에는 A공원의 야경과 A→B 이동이 함께 들어 있지만, 이동 인용만을 독립적으로 검색할 벡터는 없었다.

질문이 이동을 묻더라도 후보 진입 여부는 전체 청크를 표현한 벡터의 유사도에 달려 있었다. 원문에 관련 문장이 있다는 사실만으로 그 장소가 상위 후보에 들어오는 것은 아니었다.

이전 원인 분리 진단에서는 같은 목적지 B공원을 가리키지만 차량 전용이거나 도보 통행이 금지된 합성 방해 사례 40개를 넣었다. A공원의 올바른 보조 이동 근거는 활성 상태였지만 벡터 순위가 **41개 중 41위**였다. 기본 후보 상한 30개에서 제외돼 리랭커에 전달되지 않았다.

이 상태에서는 리랭커가 아무리 원문을 잘 읽어도 A공원을 선택할 수 없다. 리랭커는 전달받은 후보의 순서를 다시 평가하기 때문이다.

원인을 분리하기 위해 이전 진단에서만 같은 벡터와 근거의 후보 상한을 풀어 41개를 모두 리랭커에 전달했다. 그러자 A공원의 보조 이동 근거가 대표 근거로 선택됐고 A공원이 최종 1위가 됐다. 이 결과로 해당 사례에서는 후보 진입 단계의 손실이 병목임을 확인했다.

다만 “경관 정보가 임베딩의 어느 차원에 얼마만큼 영향을 줬다”는 내부 원리까지 측정한 것은 아니다. 관찰한 사실은 전체 청크 벡터로는 이동 근거가 41위였고, 이를 리랭커에 전달하면 최종 1위로 평가됐다는 것이다.

**이동 관계의 정확한 원문 인용을 검색 표현으로 추가했다.**

새 방식에서는 기존 전체 청크 벡터를 보존하면서, 선택된 활성 청크에 있는 검증된 이동 관계의 `evidence.quote`를 BGE-M3로 별도 임베딩한다. 이 사례의 추가 임베딩 입력은 다음 인용이다.

> 관람 후 B공원으로 걸어갈 수 있다.

인용 자체에는 출발지 이름이 없지만, 해당 인용은 검증된 A→B 관계에 연결돼 있다. 출발지와 도착지는 관계 정보로 관리하고, 리랭커에 근거를 전달할 때 함께 제공한다.

예상 질문을 새로 생성하거나 “A공원에서 B공원까지 가깝고 편하다”는 문장으로 바꾸지는 않았다. 원문이 말하는 도보 이동 가능성만 표현했다. 이동 시간이나 거리, 편의성은 이 인용으로 확인할 수 없다.

관계 벡터는 `retrieval_relation_embeddings`에 청크 ID, 문맥 버전, 관계 순번, 표현 버전, 원문 인용과 1024차원 벡터를 연결해 저장한다. SQL trigger는 관계 순번과 원문 위치, 인용, 관계 종류와 비중이 저장된 관계와 일치하는지 검사한다.

추가 벡터 저장은 기존 색인 세대 비교가 성공한 트랜잭션 안에서만 수행한다. 원본이나 청크 세대가 바뀐 오래된 작업이 새 관계 벡터를 덧붙이지 않도록 기존 갱신 경계를 유지했다. 관계 인용이 없는 과거 자료에는 인용을 만들어 채우지 않으며, 별도 벡터가 없으면 기존 전체 청크 벡터 경로를 사용한다.

**관계 조건을 먼저 검사하고, 가장 잘 맞는 표현 하나를 선택했다.**

이동 인용 벡터는 명시적인 이동 관찰 필터가 있는 검색에서 사용한다. 경관이나 시설 검색, 관찰 필터가 없는 검색은 기존 경로를 유지한다.

검색 시에는 출발지, 도착지, 결과로 반환할 쪽, primary/supporting 조건을 개별 관계에 적용한다. 같은 청크에 A→B와 A→C가 함께 있더라도, B를 묻는 질문에서 A→C의 높은 점수를 가져다 쓰면 안 되기 때문이다.

조건을 만족하는 각 활성 청크에서는 전체 청크 벡터와 해당 관계 인용 벡터 중 질문과 cosine 유사도가 가장 높은 표현 하나를 선택한다. 장소별로도 가장 높은 근거 점수를 사용하고 중복을 제거한 뒤 Top-30을 구성한다.

벡터가 두 개라고 점수를 더하거나, 관계가 많은 장소에 가산점을 주지는 않았다. 장소 후보 상한은 30개, 장소별 리랭킹 근거는 최대 2개로 유지했다.

관계 벡터로 검색된 근거는 그 관계의 원문 인용과 출발지·도착지를 리랭커에 전달한다. 보존된 전체 청크와 A공원·B공원의 기존 subject/mentioned 구분은 바꾸지 않는다. 검색 경로와 관계 순번도 결과 근거에 남겨 어떤 표현으로 후보에 진입했는지 확인할 수 있게 했다.

**동일한 조건에서 A공원이 후보 1위와 최종 1위에 도달했다.**

비교에서는 기존 질문 6개를 두 검색 모드로 실행했다. 두 비교군은 같은 격리 DB의 자료와 벡터를 사용하고 검색 모드만 바꿨다.

| 고정한 항목 | 조건 |
|---|---|
| 검수 승인 자료 | 합성 통제 청크 4개와 실제 자료 청크 8개 |
| 합성 방해 사례 | 차량 전용·도보 금지 사례 40개 |
| 장소별 활성 청크 | 최대 20개, 동일한 선택 결과 |
| 장소 후보 | 최대 30개 |
| 장소별 리랭킹 근거 | 최대 2개 |
| 임베딩 모델 | BGE-M3 |
| 리랭킹 모델 | BGE-reranker-v2-m3 |
| 비교 변수 | 전체 청크 벡터만 검색 / 이동 인용 벡터도 검색 |

핵심 질문인 “B공원으로 걸어서 갈 수 있는 곳”의 결과는 다음과 같다.

| 확인 항목 | 전체 청크 벡터만 | 이동 인용 벡터 추가 |
|---|---|---|
| A공원의 후보 순위 | Top-30 탈락 | **1위** |
| A공원의 리랭커 도달 | 도달하지 못함 | 도달 |
| 최종 1위 장소 | 합성 연결공원25 | **A공원** |
| A공원의 대표 근거 | 선택되지 않음 | 보조 이동 인용 선택 |

기준군의 최종 1위인 합성 연결공원25의 리랭킹 점수는 약 0.4911이었다. 이동 인용 벡터를 추가한 비교군에서 A공원의 해당 이동 근거 점수는 약 0.9121이었다. 이는 모델의 관련성 점수이며 사실일 확률을 뜻하지 않는다.

41위라는 값은 이전 전체 후보 진단에서 확인한 수치다. 이번 고정 비교에서는 기존 방식의 Top-30 탈락과 새 방식의 후보 1위·최종 1위를 확인했다. 서로 다른 실행의 수치를 같은 측정처럼 섞지 않았다.

함께 실행한 A공원 야경, B공원으로 계단을 내려가는 이동, 실제 청담도로공원 무료 주차 질문에서는 기존과 같은 장소 1위와 대표 근거를 확인했다. 이는 해당 고정 사례의 유지 결과이며, 일반 검색 전체의 품질이 보존됐다는 뜻은 아니다.

**B공원을 찾아야 하는 질문은 활성 20개 제한 때문에 여전히 실패했다.**

“A공원에서 관람 후 걸어서 갈 수 있는 공원”이라는 질문은 같은 A→B 관계를 이용해 도착지 B공원을 찾아야 한다.

실험에서 해당 청크는 A공원 쪽에서는 활성 상태였지만 B공원 쪽에서는 활성화되지 않았다. B공원에 연결 가능한 청크는 44개였고, 대상 근거의 선택 순서가 44번째였기 때문이다. 장소별 활성 상한 20개를 유지했으므로 이 근거는 B공원 검색에 사용할 수 없었다.

| 제한 | 적용되는 단계 | 이번 작업의 결과 |
|---|---|---|
| 장소별 활성 청크 20개 | 검색 가능한 근거를 선택할 때 | B공원 쪽 대상 근거는 여전히 제외 |
| 검색 후보 30개 | 질문과 비교해 장소 후보를 고를 때 | A공원은 관계 벡터로 1위 진입 |

두 제한은 적용되는 단계가 다르다. 이번 변경으로 개선한 것은 활성 상태인 근거가 후보 순위에서 밀리는 사례다. 활성 선택에서 제외된 근거를 검색 대상으로 복구하지는 않았다.

이때 “반대 질문”은 B→A로 걷는다는 뜻이 아니다. 이동 방향은 여전히 A→B이고, 질문이 출발지 대신 도착지를 요구한다는 차이다.

**장소 귀속 오류와 근거 부족도 남아 있다.**

다른 공원에 관한 설명을 청담도로공원의 설명으로 잘못 연결한 자료가 있다면, 인용을 별도로 임베딩해도 그 잘못된 연결 자체가 수정되지는 않는다. 어떤 장소를 설명하는 문장인지, 출발지와 도착지를 올바르게 판정했는지는 별도의 의미 검수가 필요하다.

고정 비교의 청담도로공원 한강 야경 질문에서도 장소는 반환됐지만 야경을 뒷받침하는 근거는 확인되지 않았다. 검색 결과에 장소가 나왔다는 사실과 질문을 뒷받침하는 근거를 찾았다는 사실은 별도로 확인해야 한다.

이번 검수는 버전을 아는 에이전트가 수행했으며 블라인드 인간 평가가 아니다. 합성 방해 자료를 포함한 작은 감독 검증이므로 전체 장소와 질문 분포를 대표하지 않는다. 길이가 다른 전체 청크와 짧은 인용 중 최대 cosine을 고르는 정책도 일반 분포에서 추가 검증이 필요하다.

**검증은 격리 환경에서 수행했고 기본 검색은 유지했다.**

해당 커밋의 기록상 서버 검사는 전체 144개 중 143개 통과, 기존 모델 플래그가 필요한 검사 1개 건너뜀이었다. Docker bootstrap·shell 검사는 13개 통과했다. 관계 방향 조건 우회 방지, 인용과 위치 불일치 거부, 후보 중복 제거, 비활성 endpoint 제외와 오래된 색인 작업의 벡터 미저장 등을 확인했다. 이 수치는 구현 당시 실행 기록이며 이 글을 작성하면서 다시 실행한 결과는 아니다.

기존 임베딩 58개를 재사용했고 새로 임베딩한 고유 문장은 4개였다. 추가 임베딩 요청은 1회, 캐시에 없던 리랭킹 입력 계산은 3회·9개 입력이었다. 같은 부정 인용은 반복 임베딩하지 않았다. 이번 비교의 Perplexity·Sonar 호출은 0회이며 운영 DB 쓰기도 0회였다.

기존 벡터와 리랭킹 점수를 재사용했고 SQL 시간도 단회 측정이므로, 이 결과로 전체 검색이 빨라졌다고 판단하지 않는다.

운영 기본값은 `CONTEXTUAL_RELATION_RETRIEVAL=chunk-only`로 유지했다. 추가 검색 경로는 `chunk-and-relation-v1`을 명시적으로 선택할 때 사용한다. 운영 적용에는 스키마 반영과 검수된 대상의 재색인이 필요하며, 설정만 바꿔도 기존 청크의 관계 벡터가 자동으로 생기는 것은 아니다. 이번 작업에서는 운영 설정과 컨테이너를 갱신하지 않았다.

이 사례를 통해 다음 검색 실패를 조사할 때 확인할 지점이 구체화됐다. 근거가 활성화돼 있는지, 후보 상한 안에 들어오는지, 리랭커가 적절한 근거를 선택하는지, 그 근거가 실제로 해당 장소와 질문을 뒷받침하는지를 단계별로 기록할 필요가 있다. 이번 이동 인용 벡터는 그중 후보 검색에서 누락되던 한 근거를 다음 단계까지 전달하는 역할을 했다.

**후속 구현: 목적지를 지정하지 않는 일반 의미 검색에도 연결했다.**

위 본문은 커밋 `1e646b33`에서 확인한 결과다. 이후 `feat/contextual-general-relation-retrieval` 브랜치에서는 관계 벡터 사용 모드의 일반 의미 검색에서도 이동 인용을 함께 조회하도록 확장했다. observation 이동 필터나 출발지·도착지 지정이 없어도 같은 질문 벡터로 전체 청크와 관계 인용을 검색한다. 질문을 먼저 이동 의도로 분류하거나 예상 질문을 생성하는 단계는 추가하지 않았다.

같은 원문의 전체 설명과 이동 인용이 근거 중복 제거에서 하나로 사라지지 않게 했고, B의 관계 슬롯에는 A의 경관을 담은 전체 청크 벡터를 사용하지 않도록 했다. 장소별 활성 20개, 후보 30개와 근거 수 예산은 유지했다. 기존 선택 설정에서 동작하며 운영 기본값은 바꾸지 않았다.

실제 BGE·PostgreSQL의 고정 질문 9개 전후 비교에서 목적지 없는 도보 질문과 야경·이동 복합 질문은 A공원 1위를 유지했다. 이 질문들은 기존 일반 검색에서도 1위였으므로 새 순위 개선으로 세지 않는다. 넓은 ‘주변 관광지와 연결된 곳’ 질문의 진단 대상 A는 여전히 최종 28위였고, B의 비활성 보조 근거도 복구되지 않았다. 서버 검사는 157개 중 156개 통과·기존 모델 플래그 검사 1개 건너뜀이었다.

구현 범위, 질문별 결과, 계산량 증가와 남은 한계는 [일반 의미 검색 통합 보고서](../../Evaluation/runs/contextual/general-relation-retrieval-v1/20261101-01/REPORT.md)에 따로 기록했다.
