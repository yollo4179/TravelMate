# 지역명 쿼리 포함 vs SQL 필터 분리 — 비교 실험 및 결론

> **목적**: 사용자 쿼리에 지역명(예: "종로")이 포함된 경우, 그 지역명을 임베딩 텍스트에
> 그대로 같이 넣는 방식과 SQL `WHERE city = ?`로 분리해서 걸러내는 방식을 실제 데이터로
> 비교하고, 어느 쪽을 채택할지 결론을 정리한다.
> **실험 환경**: PGVector + BGE-M3, 서울 관광지(TourContentType.관광지) 449건
> **관련 문서**: `nearby_search_tool_design.md` 7장(같은 내용을 tool 설계 관점에서 요약),
> `rag_search_quality_analysis.md`(이 문제의 최초 발견 지점)

**작성일**: 2026-07-12
**버전**: v1.0

---

## 1. 배경

앞선 RAG 품질 분석(`rag_search_quality_analysis.md`)에서 "경복궁 근처 가볼만한 곳" 같은
위치 기반 쿼리가 지리적 근접성을 반영 못 한다는 문제를 확인했다. 이번엔 그 다음 단계로,
**지역명이 검색어에 섞였을 때 임베딩 자체가 오염되는지**를 별도로 검증했다.

같은 의도("종로 지역에서 역사 공부하기 좋은 곳 찾기")를 두 가지 방식으로 구현해서 비교했다.

- **A안**: 지역명+테마를 한 문장으로 합쳐서 그대로 임베딩 (`"종로 역사 공부하기 좋은 장소"`),
  필터 없이 `searchSimilarTopK`로 전체 places 대상 검색
- **B안**: 지역명은 SQL `WHERE city = '종로'`로 분리해서 필터링하고, 임베딩에는
  순수 테마(`"역사 공부하기 좋은 장소"`)만 사용

참고로 지역명을 아예 안 쓴 기준선(baseline)도 같이 확보했다:

- **기준선**: `"역사 공부하고 싶어"` (지역명 없음, 필터 없음, 서울 전역 대상)

## 3. 분석

| 항목 | A안 (지역명 포함 임베딩) | B안 (SQL 필터 분리) |
|---|---|---|
| 1위 유사도 | 0.5776 (종로 무계원, 실제론 약한 매칭) | 0.5212 (성균관 명륜당, 정확한 매칭) |
| 음식점/골목 노이즈 | 2위·7위에 등장 | **없음** |
| 진짜 좋은 매칭(역사문화공원, 서원) | 8~9위로 밀려남 | 상위권 진입(경희궁공원 3위) 또는 대상에서 자연 제외 |
| 원인 | "종로"라는 지역명 텍스트가 테마 신호와 같은 벡터에 섞여, 텍스트 겹침이 강한 항목(음식 골목 등)이 유사도를 부풀림 | 지역은 구조화 필터로 완전히 분리되고, 임베딩은 순수 의미 신호만 담당 |

**핵심 발견**: A안의 1위 점수(0.5776)가 B안의 1위 점수(0.5212)보다 오히려 높다. 이건 A안이
더 잘 맞아서가 아니라, **"종로"라는 고빈도 텍스트 겹침이 유사도 점수 자체를 부풀리기 때문**이다.
절대 유사도 값이 높다고 해서 결과가 더 정확한 게 아니라는 뜻 — 이 프로젝트에서 유사도 점수를
품질 지표로 그대로 신뢰하면 안 되는 이유이기도 하다.

## 4. Solution (결론)

**지역/카테고리 등 메타데이터는 절대 임베딩 텍스트에 섞지 않고, SQL 구조화 필터로 분리한다.**

- `PlaceVectorRepository.searchSimilar(embedding, region, city, category, minSimilarity, k)`는
  이미 이 구조를 지원하도록 만들어져 있었음 (코드 변경 불필요) — 문제는 **호출하는 쪽**이
  지금까지 지역명까지 한 문장으로 합쳐서 임베딩해왔다는 것.
- 실제 서비스에서는 사용자의 자연어 요청("종로에서 역사 공부하기 좋은 곳")에서 지역명(`city`)과
  순수 테마(`query`)를 분리해서 넘겨야 한다. 이 분리 작업은 **LLM이 tool calling으로 검색 툴을
  호출할 때 인자를 구성하는 과정**에서 자연스럽게 수행하도록 설계한다
  (`search_places_semantic(query, region, city, category, limit)` — `nearby_search_tool_design.md` 7장 참고).
- 별도의 규칙 기반 지역명 추출기(NER 등)를 만들 필요는 없다 — LLM이 이미 이 분리를 잘 해낼 수 있고,
  tool description에 "지역명은 query에 넣지 말고 city/region으로 분리하라"는 지침만 명시하면 된다.

**남은 한계**: B안에서도 여전히 "약한 관련"으로 표시된 항목들(종로 무계원, 호전다실, 인사동 등)이
중위권에 남아있다. 이건 지역 오염 문제가 아니라 순수 벡터 검색 자체의 한계("서래마을"류, 문체는
비슷한데 주제는 다른 오탐)라 재랭킹이나 쿼리 재작성으로 별도 개선이 필요하다 (우선순위 낮음).
